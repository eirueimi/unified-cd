## W0-1 — PgBouncer transaction pooling causes silent leader-election split-brain and duplicate schedule fires
- **Invariant:** I1 (run accounting)
- **Severity:** major
- **Repro:** `test/edgecase/scenarios/w0-1-pgbouncer-txn-pooling.md`, probe section (observation steps 1-5). Baseline (no overlay) confirmed healthy first: single leader (`controller2`), 2 runs in ~90s from a 1/min schedule, SSE streaming live `tick N` events. Probe stacked `../edgecase/compose/pgbouncer.override.yaml` (all three controllers' `UNIFIED_DB_DSN` routed through `pgbouncer` in `POOL_MODE: transaction`) onto the same compose file and repeated the job+schedule apply.
- **Observed:** All three controllers independently logged `"scheduler became leader"` within an 11-minute window, with no corresponding "lost leadership"/"stepped down" message ever logged by any of them:
  ```
  controller1-1 | {"time":"2026-07-29T01:47:53.589Z","level":"INFO","msg":"scheduler became leader"}
  controller2-1 | {"time":"2026-07-29T01:57:06.415Z","level":"INFO","msg":"scheduler became leader"}
  controller3-1 | {"time":"2026-07-29T01:57:09.477Z","level":"INFO","msg":"scheduler became leader"}
  controller1-1 | {"time":"2026-07-29T02:05:18.889Z","level":"INFO","msg":"scheduler became leader"}   # re-claimed, no restart/kill involved
  ```
  From the moment all three had claimed leadership, `edge-every-minute` fired **3x per cron tick** instead of once (`GET /api/v1/runs?jobName=edge-tick` sample, one minute's worth):
  ```
  createdAt: 2026-07-29T01:57:06.418461Z  triggeredBy: schedule:edge-every-minute
  createdAt: 2026-07-29T01:57:09.479238Z  triggeredBy: schedule:edge-every-minute
  createdAt: 2026-07-29T01:57:54.540495Z  triggeredBy: schedule:edge-every-minute
  ```
  Run count grew from 0 to 26 in ~10 minutes (expected-healthy ~10). No `advisory`/`lock`/`unlock`-related log line ever appeared on any controller — `grep -i "advisory\|lock\b\|unlock"` over all three logs matched nothing but the routine `"postgres pool configuration"` line. `pg_locks` (queried directly against `postgres`, bypassing the pooler) showed a stable set of 6 granted advisory locks held by only 3 distinct Postgres backend pids (68, 69, 282) throughout (observed interactively; raw query output not captured — re-capture when this scenario is promoted to a permanent test) — i.e. PgBouncer's small pool of *real* server-side sessions is shared/multiplexed across the three controllers' logical connections, so a lock "held" by one controller's client connection is actually attached to a shared backend session another controller's transaction can just as legitimately borrow next. That is the mechanism behind the split-brain: it produces zero Postgres-level lock errors because, from Postgres's point of view, every acquire/release is happening on a real, valid session — the pooling layer is what silently reassigns "the same" session identity to different application-level leaders. Restarting `controller1` (kill+recreate) and waiting 60s did not strand any lock (still 6 granted, no dead/orphaned pids) and did not stop the split-brain — it simply re-joined and re-claimed leadership on its own 90s later, unprompted. Killing the apparent last-elected leader (`controller3`) did not halt scheduling either: runs kept accumulating afterward (26 -> 27 -> 28 -> 28 -> 30 -> 30 over ~106s) at roughly the reduced (2-leader) duplicate rate, driven by the two survivors.
- **Expected:** `docs/high-availability.md` requires session pooling and states that transaction pooling "breaks advisory locks and NOTIFY." The expected failure mode per the docs would be lock breakage; what we could not tell from the docs alone is whether that breakage is loud (errors an operator could alert on) or silent. It is the latter: no error, warning, or lock-contention message of any kind was logged anywhere in the stack; the only externally visible symptom is the schedule firing 2-3x too often and multiple `"scheduler became leader"` lines across replicas that a log-scraping alert would need to specifically watch for.
- **Notes:** Recommend the docs/runbook explicitly call out that the failure signature is "duplicate `scheduler became leader"` lines across >1 controller ID" and "run count exceeding schedule cadence," since there is no explicit split-brain or lock-loss error to grep for. A cheap mitigating fix: emit a "scheduler lost leadership" (or periodic leader-lock renewal failure) log line distinct from "became leader," so flapping is visible without cross-referencing run timestamps. Also worth an invariant check (I1) at the run-creation layer: reject/dedupe schedule-triggered runs for the same schedule tick within a short window, independent of leader-election correctness, as defense in depth.

## W0-1 — Controllers crash-loop with no DB-connect retry at startup; pgbouncer overlay reliably triggers it via a boot race
- **Invariant:** I5 (bounded recovery — diagnosability)
- **Severity:** minor
- **Repro:** Same probe as above, `docker compose -f docker-compose.ha.yaml -f ../edgecase/compose/pgbouncer.override.yaml up -d --build` cold start (not a steady-state observation — this happened on the very first `up`).
- **Observed:** Two of three controllers exited immediately on first boot because they queried Postgres (via `pgbouncer`) before PgBouncer's listener/DNS record was fully live, and neither retries:
  ```
  controller2-1 | {"level":"ERROR","msg":"store init","error":"ping postgres api pool: failed to connect ... connection refused"}
  controller3-1 | {"level":"ERROR","msg":"store init","error":"ping postgres api pool: ... lookup pgbouncer on 127.0.0.11:53: no such host"}
  ```
  Both processes then exited(1) rather than retrying, which in turn made `nginx` (whose upstream config lists all three controllers by DNS name at startup) fail to start at all, since Docker's embedded DNS had already dropped the dead containers' records:
  ```
  nginx-1 | 2026/07/29 01:47:53 [emerg] 1#1: host not found in upstream "controller2:8080" in /etc/nginx/nginx.conf:7
  ```
  This cascaded to `agent-enroll` looping on `dial tcp: lookup nginx ...: no such host` for its full 60-retry budget and exiting with `controller never became ready for agent1`, leaving the compose `up -d --build` command itself reporting a failure even though `postgres`, `pgbouncer`, and `controller1` were all healthy. Manually re-running `docker compose up -d controller2 controller3 nginx` (letting them retry against an already-warm pgbouncer) then `up -d agent-enroll agent1 agent2` recovered the stack fully with no further errors.
- **Expected:** A transient dependency race at boot (a sibling container's DNS/listener not yet ready) is the kind of condition a clustered controller should retry through, not crash-exit on — especially since `postgres`/`pgbouncer` already gate `depends_on: condition: service_healthy` for the DB but there is no equivalent healthcheck/retry for the controller-to-pgbouncer hop or for nginx-to-controller DNS resolution.
- **Notes:** Not unique to transaction-pooling mode — a plain extra network hop (any TCP proxy in front of Postgres) would likely reproduce it — but the pgbouncer overlay is what surfaced it here since it's the first scenario in this campaign to insert a proxy between controller and Postgres. Recommend either a startup retry loop on `store init` (bounded, with backoff) or a `depends_on: condition: service_healthy` + healthcheck on the `pgbouncer` service itself so controllers don't race it.

## W0-1 — SSE/NOTIFY log streaming keeps working under transaction pooling, despite the docs' blanket claim
- **Invariant:** I5 (bounded recovery — diagnosability / docs accuracy)
- **Severity:** minor
- **Repro:** Same probe stack (pgbouncer overlay active, split-brain already underway). Attached to a currently-running run's SSE endpoint: `curl -N --max-time 15 "localhost:18080/api/v1/runs/cc467bdc-8853-48b8-9973-b4e5ec609ada/events" -H "Authorization: Bearer ha-admin-token"`.
- **Observed:** Log lines streamed live and in order, same shape as the healthy baseline — no stall, no gap, no reconnect needed:
  ```
  data: {"type":"log","seq":541,"stepIndex":0,"stream":"stdout","line":"tick 1","timestamp":"2026-07-29T02:02:57.998135Z"}
  data: {"type":"log","seq":542,"stepIndex":0,"stream":"stdout","line":"tick 2","timestamp":"2026-07-29T02:02:57.998135Z"}
  data: {"type":"log","seq":543,"stepIndex":0,"stream":"stdout","line":"tick 3","timestamp":"2026-07-29T02:02:59.99823Z"}
  ...
  data: {"type":"log","seq":552,"stepIndex":0,"stream":"stdout","line":"tick 12","timestamp":"2026-07-29T02:03:08.005493Z"}
  ```
  (full capture not committed; `seq` increments continuously, `curl` received bytes throughout the 15s window rather than blocking until timeout.)
- **Expected:** `docs/high-availability.md` states transaction pooling "breaks advisory locks and NOTIFY," which reads as a blanket claim covering both mechanisms. Advisory locks did break (see the split-brain entry above), but NOTIFY-driven SSE delivery did not visibly break in this run — an operator reading the docs literally would expect log streaming to also stall or go silent under this misconfiguration, and it didn't.
- **Notes:** Either the controller's SSE/log-delivery path doesn't actually depend on LISTEN/NOTIFY the way the docs imply (e.g. it falls back to polling, or the connection happened to land on a session that kept a live LISTEN registration for the run's duration), or NOTIFY breakage requires conditions this run didn't hit (e.g. longer runs, more concurrent listeners, a pooler reconnect mid-stream). Recommend either correcting the docs to be precise about which mechanism breaks (advisory locks, confirmed) versus which is untested/unconfirmed (NOTIFY), or a follow-up scenario specifically designed to stress LISTEN/NOTIFY under transaction pooling (e.g. a long-running job with a mid-run pgbouncer server-connection cycle) before asserting NOTIFY breakage as fact.

## W0-2 — TZ-divergent replicas disagree on whether a schedule is due for the same physical instant
- **Invariant:** I1 (run accounting)
- **Severity:** major
- **Repro:** `go test -tags edgeprobe ./internal/controller -run TestEdgeProbe_TZDivergentLeaders -v` (`internal/controller/edgeprobe_scheduler_test.go`).
- **Observed:** A UTC-context check and a JST-context check of the exact same schedule (`"0 9 * * *"`) at the exact same physical instant (00:05 UTC vs 00:06 UTC — one minute apart, but the schedule's own `next`/due computation is evaluated against `now.In(<replica's Location>)`) reach opposite due/not-due conclusions:
  ```
  edgeprobe_scheduler_test.go:134: UTC-leader fired=0, JST-takeover fired=1, last_fired_at=2026-07-29 09:00:00 +0900 JST — TZ divergence causes skip/dup? utc=0 jst=1
  ```
  The UTC-context leader sees the schedule as ~9h from due (`fired=0`); the JST-context leader, checking essentially the same moment, sees `09:06 JST` and fires it (`fired=1`). Nothing in the run-creation path detects or reconciles this — whichever replica happens to be leader when it evaluates `now` in its own Location wins, silently.
- **Expected:** Cron due-ness should be a property of the physical instant plus the schedule definition, not of which `time.Location` happens to be attached to the `now` value a given leader passes into `dsl.NextCronTime`/`checkAndFireSchedules`. A schedule should fire exactly once per intended occurrence regardless of which replica (or which replica's local/env TZ) is currently leader.
- **Notes:** This is the most concerning result from the W0-2 batch (per Task 5's analysis) because it is a live architectural landmine, not a rare boundary condition: any HA deployment where replica hosts/containers don't have `TZ` pinned identically (or where `now` is constructed via `time.Now()` on hosts with different local zones, or passed through `.In(...)` inconsistently anywhere in the call chain) is exposed to this on every leader handoff, producing either a duplicate fire (if the new leader's Location makes an already-fired occurrence look due again) or a skipped fire (the reverse). Recommend: (1) normalize `now` to UTC at every entry point that computes cron due-ness, never trusting an arbitrary Location on the caller-supplied timestamp; (2) add a startup/health check that asserts all controller replicas report the same effective TZ; (3) treat this as a strong argument for pinning `TZ=UTC` in the HA compose/deployment manifests explicitly rather than leaving it to host defaults.

## W0-2 — Catch-up window boundary: an occurrence missed by one cron interval (5 min) past the 1h window is silently and permanently dropped
- **Invariant:** I1 (run accounting), I5 (bounded recovery — diagnosability)
- **Severity:** major
- **Repro:** `go test -tags edgeprobe ./internal/controller -run TestEdgeProbe_CatchupWindowBoundary -v` (`internal/controller/edgeprobe_scheduler_test.go`).
- **Observed:** The closed lower edge of the catch-up window (`next == now-60m` exactly) correctly fires:
  ```
  edgeprobe_scheduler_test.go:81: boundary next==now-1h: fired=1 last_fired_at=2026-07-29 20:00:00 +0900 JST
  ```
  But one cron interval (5 minutes, the `*/5` schedule's own granularity) further out (`next == now-65m`, from a `last_fired_at` seeded at `now-66m` = 19:54 JST), the occurrence is dropped with zero signal of any kind:
  ```
  edgeprobe_scheduler_test.go:89: just outside window: new-runs=0 (silent skip? true) last_fired_at=2026-07-29 19:55:00 +0900 JST
  ```
  No run is created, and there is no log line, error, warning, or metric distinguishing "occurrence intentionally outside catch-up window, dropped" from "nothing was due yet." `last_fired_at` IS advanced to the skipped occurrence (19:55 JST, i.e. the `next` value) — `internal/controller/scheduler.go:197-201` takes this path unconditionally when `next < windowStart`, so the run is dropped but the bookkeeping still moves on. The only trace that an occurrence was silently lost is the absence of a run row a human would have to know to go looking for; nothing distinguishes this `last_fired_at` advance from the one that happens on a normal fire.
- **Expected:** A 1-hour catch-up window is a reasonable, presumably intentional bound (I5 — "bounded recovery"), but a schedule occurrence that falls outside it should be a detectable event, not indistinguishable from normal steady-state operation. An operator recovering from an outage that lasted a few minutes longer than the window gets no indication that a tick was lost.
- **Notes:** Argued as **major** primarily because the missed occurrence is *permanently* lost, not merely delayed — no catch-up ever happens for it, unlike the backward-clock-step or DST-gap entries below where the affected occurrence is late but still eventually fires. A scheduled run that was due and never executes at all is incorrect behavior in its own right (silent data loss against I1, run accounting), independent of how loud or quiet the failure path is. The total silence (no log line, error, warning, or metric distinguishing this from steady-state) is an aggravating factor that compounds the severity — it means operators cannot even detect after the fact that an occurrence was dropped — but is not itself the primary basis for the major rating; on diagnosability alone this would only be minor per this file's own severity rubric. Not critical, because it's a single bounded occurrence rather than ongoing/systemic corruption, and the window's existence is itself a documented, intentional design choice. Per a reading of `scheduler.go:197` (`next < windowStart → too old to fire`), this silent-drop path applies to any occurrence outside the window by any margin, not just the 5-minute case the probe exercised — that broader claim is inferred from the code, not directly demonstrated by this probe. Recommend at minimum a `WARN`-level log line (`"schedule occurrence outside catch-up window, skipped"`, with schedule ID and how far outside) whenever this path is taken.

## W0-2 — observation: backward clock step causes a bounded, self-healing stall equal to the skew magnitude
- **Invariant:** I1 (run accounting)
- **Severity:** minor
- **Repro:** `go test -tags edgeprobe ./internal/controller -run TestEdgeProbe_BackwardClockStep -v` (`internal/controller/edgeprobe_scheduler_test.go`).
- **Observed:**
  ```
  edgeprobe_scheduler_test.go:151: with future last_fired_at: fired=0 (every-minute schedule silent until wall clock catches up: true)
  ```
  A `last_fired_at` stamped 10 minutes in the future (e.g. from a leader with a fast/skewed clock) causes an every-minute schedule to stop firing when checked against the real, correct `now`. This is bounded and self-healing: because the scheduler only fires when the computed `next` time is after `last_fired_at`, the schedule resumes on its own — no operator action, no restart, no manual reset — as soon as real wall-clock `now` catches up past the erroneous future stamp. The stall duration equals the skew magnitude (~11 minutes for the tested 10-minute-ahead skew, given the every-minute cadence); no occurrence is permanently lost, and the schedule is back to normal cadence immediately once the clock passes the bad timestamp. Structurally this is the same recovery shape as the DST-gap entry below (single bounded delay, automatic resumption, no data loss), not an unbounded one.
- **Expected:** A future `last_fired_at` from clock skew is a fault condition; recovery should be bounded once the underlying skew is no longer ahead of real time. Observed behavior matches this: the delay is bounded by, and directly proportional to, the size of the skew, with no manual intervention required.
- **Notes:** Rated minor rather than major, consistent with the DST-gap entry's rating for the same recovery shape. Caveat/extrapolation beyond what was directly observed: the probe only exercised a 10-minute skew, and nothing in the observed logic caps how large a skew can be written to `last_fired_at` in the first place — a much larger erroneous future stamp (from a badly corrupted clock, NTP misconfiguration, or a bug elsewhere writing a bogus timestamp) would plausibly produce a proportionally longer stall of the same bounded/self-healing shape, but potentially large in wall-clock terms, and it would be silent and undetectable for its entire duration (no metric or log flags "schedule N minutes overdue due to a future last_fired_at"). This is inferred, not tested — the probe does not establish how large a skew the system will tolerate before writing `last_fired_at`, if there is any limit at all. If large-skew robustness is a real operational concern, recommend clamping/rejecting `last_fired_at` writes that are ahead of the server's own `now` (`pg.UpdateScheduleLastFiredAt`) as defense in depth, and/or a health check comparing each schedule's expected next-fire time to wall clock — a hardening suggestion, not evidence of an unbounded defect as tested.

## W0-2 — DST spring-forward gap: a daily schedule silently skips the transition day instead of firing near the gap
- **Invariant:** I1 (run accounting)
- **Severity:** minor
- **Repro:** `go test -tags edgeprobe ./internal/controller -run TestEdgeProbe_DSTGap -v` (`internal/controller/edgeprobe_scheduler_test.go`).
- **Observed:**
  ```
  edgeprobe_scheduler_test.go:46: DST gap: next('30 2 * * *') after 2026-03-08 01:00:00 -0500 EST = 2026-03-09 02:30:00 -0400 EDT (skipped? true)
  ```
  `02:30` does not exist on 2026-03-08 in `America/New_York` (clocks jump 02:00 -> 03:00). `dsl.NextCronTime` does not fast-forward to the nearest valid time on the same day (e.g. 03:30) or fire once at the gap boundary — it skips the entire remainder of March 8th and returns March 9th's `02:30 EDT` instead, a ~24h delay versus the schedule's nominal daily cadence.
- **Expected:** Not explicitly documented behavior either way, but an operator reading `"30 2 * * *"` as "runs daily at 2:30am" would not expect a full calendar day to be skipped on the two-per-year DST transition dates without any indication.
- **Notes:** Kept at minor rather than major because the recovery is bounded and predictable (exactly one missed occurrence, resuming automatically the next day at the correct time — this is standard, if under-documented, behavior for cron libraries using wall-clock arithmetic over a `Location`), and it affects at most one occurrence twice a year for daily-or-coarser schedules in DST-observing zones. Worth a one-line callout in scheduling docs ("schedules that land in the spring-forward gap skip to the next valid occurrence rather than firing early/late on the same day") so this isn't a support-ticket surprise.

- **Expected:** `docs/troubleshooting.md`'s documented behavior for a `LogPusher` under sustained controller/DB unreachability is bounded local buffering with a `[N log line(s) dropped: controller unreachable]` marker on cap overflow — i.e. loss is meant to be loud and to only happen once >1MiB of a single step's output is buffered during an outage. What actually happened is a **different, silent** loss path: a comparatively brief (~74s) outage that happens to still be ongoing at the exact moment a step finishes locally can drop the entire unflushed tail with no marker at all, regardless of how little data was buffered, because the step-end `Flush` gets only a fixed ~5s exit-time retry rather than the same unbounded-retry treatment given to run/step status reporting.
- **Notes:** This is a distinct mechanism from the (correctly-documented, marker-emitting) 1MiB pending-cap eviction path noted as untested-but-present in the W1-1 entry above and in the prior agent-failsafe audit's F9 finding (`unified-cd-audit-findings` memory: "agent LogPusher 1MiB silent drop") — F9 is about the cap; this is about the **step-end bounded retry window**, which can lose data at any size, including far below the cap, as long as the outage outlasts ~5-9s and is still ongoing when the step naturally finishes. W1-1's outage (all three controllers, ~81s) never hit this path because it started and ended entirely *before* the step's natural completion, so the 2s ticker had many chances to drain `pending` well before `finish()` ever ran. This scenario's variant B outage happened to overlap the step's tail by construction (the forced kill landed ~38s before local completion). Recommend either: (a) give the step-end `Flush` the same unbounded `retryUntilSuccess` treatment as `ReportStep`/`FinishRun` (bounded only by a much longer ceiling, or by the same `stepCtx`/process-exit horizon), or (b) if a bounded exit-time retry is intentional (e.g. to avoid indefinitely blocking process shutdown), at minimum increment `droppedLines` (or an equivalent one-shot log/metric) for whatever remains in `pending` when `Flush` gives up — today the existing `[N line(s) dropped]` marker can't help here even in principle, since it fires only when `droppedLines > 0` (set exclusively by `appendPendingLocked`'s cap-eviction path) *and* a later successful flush occurs; this loss satisfies neither condition — the lines are abandoned in `p.pending` without ever being evicted, and no later flush call happens at all for that `LogPusher` instance.

- **Observed:** Postgres's own log shows it immediately began rejecting *new* connections (`FATAL: the database system is shutting down`, first occurrence `05:22:05.662Z`, repeating every ~2s indefinitely), matching PostgreSQL's standard SIGTERM ("Smart Shutdown") semantics: refuse new sessions, wait for existing ones to end on their own before the postmaster exits. - **Expected:** The runbook (`test/edgecase/scenarios/w1-2-postgres-restart.md`) anticipated `kill-soft` producing a comparable-but-gentler outage to `kill-hard`, so hard-vs-soft controller reconnect latency could be compared directly. That assumption doesn't hold: with a connection pool that holds idle sessions open indefinitely (as unified-cd's controller does — no idle-connection eviction was observed to kick in within several minutes), a plain `SIGTERM` to Postgres is **not equivalent to an outage at all** from the application's point of view, for as long as the pool's existing connections remain valid. This is standard, documented PostgreSQL behavior (Smart Shutdown), not a unified-cd bug, but it means "compare hard-kill vs soft-kill controller reconnect latency" isn't answerable by directly killing `postgres` with `SIGTERM` in this compose setup without also forcing new-connection-only traffic (e.g. killing/recreating the controllers' pooled connections, or using `pg_ctl stop -m fast` distinctions, or waiting substantially longer / actively closing controller connections) — a caveat worth folding into the runbook.
- **Notes:** `test/edgecase/scenarios/w1-2-postgres-restart.md`'s variant B section has been updated with a caveat block covering this exact behavior (SIGTERM will not bring postgres down while pooled connections stay open; escalate to `kill-hard` as this probe did) so the runbook stays re-runnable without re-discovering the same 3-minute stall. For a true "clean shutdown" comparison in a future run, either (a) reduce the controller's DB pool idle-connection lifetime so Smart Shutdown can complete in a reasonable window, or (b) use `pg_ctl stop -m immediate`/`SIGQUIT` inside the postgres container instead of a container-level `SIGTERM`, which forces existing backends to terminate rather than waiting for them.

## W1-3 — observation, Part B: the two independent timeout clocks (agent-local deadline vs controller-side reaper) fire at very different wall-clock times across a restart, but settle to agreeing terminal states with no I7 disagreement
- **Invariant:** I1 (run accounting), I7 (approval/gate integrity)
- **Severity:** minor (observation — confirms designed/expected behavior, no defect)
- **Repro:** `test/edgecase/scenarios/w1-3-approval-gate-restart.md`, Part B. Triggered a fresh `edge-approval` run `7efd96b1-7a36-4553-b2d3-07474f2a94c0` at `T0="2026-07-29T05:53:17.658965Z"`; gate reached `Pending` with `stepIndex:1`, `createdAt:"2026-07-29T05:53:18.04492Z"`, `timeoutAt:"2026-07-29T06:03:18.044533Z"` (10-minute `timeoutMinutes` from the job spec). Left it un-decided. Killed all three controllers hard at `06:01:58-06:02:01Z` (~T+8m43s, ~76s before `timeoutAt`), held the outage past `timeoutAt` (`readyz` 502 on every check `06:02:10Z` through `06:04:21Z`), restarted at `06:04:38-06:04:39Z` (~T+11m20s, ~80s after `timeoutAt`). `readyz` returned to `200` at `06:05:05Z`.
- **Observed:** The two clocks fired at very different times, exactly per the two-independent-mechanisms design described in the runbook:
  - **Agent clock (fires on schedule, mid-outage, controller-reachability-independent):** `agent1`'s log shows `{"time":"2026-07-29T06:03:18.098984806Z","level":"WARN","msg":"approval timed out","runID":"7efd96b1-7a36-4553-b2d3-07474f2a94c0","step":"gate"}` — **54ms after** the server-stamped `timeoutAt` (`06:03:18.044533Z`), and while all three controllers were still down (restart didn't happen until `06:04:38Z`, 80s later). Immediately preceding it: `{"time":"...098956259Z","msg":"approval poll failed",...,"error":"http 502..."}` (the same-iteration poll failing, confirming the deadline check fired independent of a successful poll) and immediately following it, the run's step-failure path begins its `FinishRun` retry loop: `{"time":"...100525048Z","msg":"retrying after failure","error":"http 502...","nextWait":1000000000}`, then doubling (`2s, 4s, 8s, 16s, 32s`) with waits capped at 32s per `RetryMaxWait` (matching the backoff-lag mechanism recorded in the W1-2 findings above), landing on a scheduled attempt at `06:04:53.119629539Z + 32s ≈ 06:05:25.12s` — which is exactly when the run's `updatedAt` timestamp lands (see below). The `FinishRun` call is wrapped in the unbounded `retryUntilSuccess` (`orchestrator.go:787`), unlike the single best-effort `ReportStep(Failed)` call for the gate step itself (`orchestrator.go:363-366`, no retry wrapper) — no log line confirms whether that specific step-level report ever landed, but it doesn't need to: the run's terminal status is carried by the retried `FinishRun` call regardless.
  - **Controller clock (fires only after restart, on the reaper's next tick):** `controller2`'s log shows `{"time":"2026-07-29T06:05:39.49764867Z","level":"INFO","msg":"approval reaper: marked timed-out approvals","count":1}` — **2m21s after** the agent's local timeout, and only after controllers had been back up for ~1 minute (readyz 200 at `06:05:05Z`), consistent with `RunApprovalReaper`'s 1-minute tick interval (`approval_reaper.go:26-27`) plus advisory-lock/leader-election bootstrap time after the restart.
  - **Final settled state (I7):** run `status:"Failed"`, `updatedAt:"2026-07-29T06:05:25.12777Z"`; approval row `status:"TimedOut"`, `decidedBy:"system"`, `decidedAt:"2026-07-29T06:05:39.494991Z"`. **The run's terminal `Failed` status was actually written ~14s before the row's `TimedOut` status** — the agent-driven `FinishRun` retry succeeded first (once the DB/controllers were reachable and its already-scheduled 32s backoff wait elapsed), and the controller-side reaper caught up to mark the row a tick later. `GET /runs/<id>/logs?after=0` after settling showed only the single `before-gate` line (seq 3) — no `after-gate` — confirming the run never resumed past the gate. No double-timeout, no conflicting writes, no `Approved` row, no re-decided row: `decidedBy:"system"` (the reaper) is the only actor that ever wrote a decision to this row.
- **Expected:** Per I7, once both clocks have settled the row and the run must agree — they need not settle *simultaneously*, since nothing documents that as a promise, only that the eventual verdicts must not contradict. Observed: `TimedOut` row + `Failed` run is exactly the expected pairing, and it was reached via two genuinely independent mechanisms (agent-local wall-clock deadline vs controller-side leader-only reaper tick) racing across a ~2.5-minute controller outage without ever producing a contradiction, a lost approval, or a double-decided row. **Caveat — this "I7 holds" verdict describes only what was actually executed in this probe (nobody attempted a decision during the gap); it is not a guarantee that the window is safe in general** — see the code-confirmed hazard below, which this probe's own timeline exposes but did not trigger.
- **Caveat (code-confirmed, not executed in this probe — repro lead for a future C11/W2-8 scenario):** during the ~14s+ window this run itself produced — run wrote `Failed` at `06:05:25.128Z` while the approval row still read `Pending` (it wasn't marked `TimedOut` until `06:05:39.495Z`) — the row was **not protected against a decision being accepted**. `handleDecideApproval` (`internal/controller/api_approvals.go:13-54`) performs no run-status lookup anywhere in the handler (no call to a run-fetching method, no join, no status comparison against the run) before calling `s.store.DecideApproval`. `DecideApproval` itself (`internal/store/postgres.go:2417-2428`) guards the `UPDATE` exclusively on the approval row's own status column — `WHERE run_id = $1 AND step_index = $2 AND status = 'Pending'` (`internal/store/postgres.go:2421`) — with no reference to the run's status at all. Consequently, an `approve` (or `reject`) POST landing anywhere in that ~14s+ (or longer, in a slower-recovery case) Pending-row/Failed-run window would satisfy the `status = 'Pending'` guard, return `204`, and write `Approved`/`decidedBy`/`decidedAt` onto a row whose run had *already* terminally `Failed` — producing exactly the C11-class contradiction this campaign is watching for (an `Approved` audit row paired with a `Failed` run), via ordinary API use, no restart or injection required beyond what already reproduces the window (an outage that lets the agent's local timeout fire and `FinishRun` land before the controller-side reaper marks the row). Not filed as a violation here because no such POST was attempted in this probe (Part B's design was "let it sit, do not approve") and the window observed live was a `Pending`/`Failed` pairing, not a produced `Approved`/`Failed` contradiction — but the missing guard is real and code-confirmed, and a scenario that races a `decide` POST against this exact window (widen it deliberately, e.g. by slowing controller recovery, then fire the POST mid-window) is a precise, ready-to-run repro lead for W2-8 or a dedicated C11 probe.
- **Notes:** No violation as executed, but three things worth flagging for a future hardening pass: (1) the missing run-status guard on `DecideApproval` above — the fix, if desired, would be adding a run-status check (either a `JOIN`/subquery against `runs.status` in the `UPDATE ... WHERE`, or a pre-check in the handler) so a decision cannot be written once the run has already reached a terminal status; (2) the step-level `ReportStep(Failed)` call on the approval-timeout path is a single best-effort attempt with no retry wrapper (`orchestrator.go:363-366`), so under an outage that starts before the agent's local deadline fires (as here), that specific step-status write is likely lost even though the run-level `FinishRun` status is not — the *step* table may show the gate step's last-known status as something other than `Failed` (not independently re-verified in this probe; the run-level outcome was the focus per the brief) even though the run itself correctly reports `Failed`; (3) the ~2m21s gap between the agent's local timeout and the controller row catching up is itself a direct instance of the "reaper can only run once a controller is up and has ticked" design already called out in the runbook and is bounded (worst case ≈ outage duration + up to 1 reaper interval), not unbounded, so it does not itself rise to an I5 concern at the durations tested here.

- **Invariant:** I7 (state display consistency — run status vs reality) violated; I1 (run accounting — every API-accepted run reaches exactly one terminal state) held throughout, including here — the run does settle on exactly one terminal state, it is simply the wrong one, which is an I7 concern, not an I1 one.
- **Severity:** major

The 60s claim grace (`claimed_at`+60s = `12:10:18.72Z`) did expire, but the grace clause is a conjunct, not a trigger: expiring it only makes a run *eligible* for the staleness test it never came close to failing. Raw evidence in the scratchpad: `w1-5/addendum-inject.txt`, `w1-5/addendum-timeline.txt`, `w1-5/addendum-evidence.txt`, `w1-5/agent1-full.log`, `w1-5/derived-counts.txt`.

  agent1-1 | {"time":"2026-07-29T12:09:46.758941554Z","level":"ERROR","msg":"permanent error, giving up retry","status":403,"error":"response omitted"}
  ```

      slog.Error("permanent error, giving up retry", "status", httpErr.StatusCode, "error", httpErr.Body)
      return
  }

  — so the otherwise-unbounded retry loop that W1-1/W1-2 measured absorbing 5xx outages for tens of seconds (~81s in W1-1's all-controller-restart entry, `FINDINGS.md:164`; ~114s of Postgres downtime in W1-2's hard-kill entry, `FINDINGS.md:204`) gives up on the **first** 4xx and never tries again, including after the partition heals. `grep -n "permanent error" w1-5/agent1-full.log` shows exactly four such lines across this whole scenario (`12:05:30.358`/`.359` for the main probe's run, `12:09:46.758`/`.759` for this one) and nothing after either heal.

The healed agent no longer listed the run as active (its goroutine had exited at `12:09:46`), so the controller correctly concluded "orphaned" — from the control plane's point of view there was never any evidence the step succeeded.
  - **The step's output is gone.** `GET /api/v1/runs/4be51a4f-.../logs?after=0` returns `[]` and `/logs/stats` returns `{"count":0,"maxSeq":0,"minSeq":0}` — the `done-short` line was never delivered and no `[N log line(s) dropped: controller unreachable]` marker exists.
  - **Caveat on the success claim, stated precisely:** the step's exit code was never delivered (that is the defect), so "it succeeded" is an inference from (a) the step being deterministic and unable to fail, and (b) the abandoned reports being timestamped at exactly `claimed_at`+28s, which is where a completed `sleep 25` lands. That the true outcome is *unobservable from the control plane* is itself part of the finding.
- **Expected:** Per I7, a run's recorded status must not contradict reality; per I1 a run must reach exactly one terminal state, and the documented failure semantics for an agent that is merely unreachable are the buffer-and-retry-until-success behavior W1-1 and W1-2 measured for 5xx outages (`retryUntilSuccess`, unbounded, doubling to a 30s cap). Treating a 4xx as permanent is defensible for a **controller-originated** 4xx — a `403` from `agentRunGuard` genuinely means "this run is claimed by another agent" (`internal/controller/agent_guard.go:121-128`) and retrying it forever would be pointless. The gap is that the agent cannot tell a controller-originated 4xx from one minted by anything in the network path, and treats both as unrecoverable.
- **Notes — injection-artifact caveat, read this before triaging:** the `403` here came from **nginx's IP deny**, which is how this campaign injects a one-way partition (the agent image has no `iptables` and no `NET_ADMIN`, so a packet-level partition is not injectable). A *real* packet-level partition would surface connect timeouts / transport errors, which are **not** `HTTPError`s and would therefore have been retried normally — so this scenario's specific trigger is an artifact of the mechanism. What is **not** an artifact is the code path: `retry.go:33-36` keys on status code alone, with no notion of who produced it, so any intermediary that transiently answers 4xx puts a run into this state. Realistic production triggers with the same shape: an ingress/WAF/service-mesh ACL briefly denying (`403`), a rate limiter shedding agent reports (`429`), or a `404` window while an ingress route is reconfigured — none of which are the controller saying "give up". Rated **major** rather than minor because the resulting status is *wrong* (not merely late or undiagnosable), *permanent* (no mechanism ever revisits it — the reconcile that settled it is itself acting on the missing report), and *actively misleading*: an operator or downstream automation seeing `Failed` would re-run a job whose side effects have already landed, which is exactly the duplicate-side-effect outcome the stuck-run reaper's own fail-never-requeue design exists to prevent (`internal/controller/stuckrun_reaper.go:72-73`). Not critical: no corruption, no security impact, and the run does still settle on exactly one terminal state. Fix directions, in increasing cost: (a) exclude `408`/`429` and, more importantly, distinguish controller-originated 4xx from intermediary-originated ones (e.g. require a controller-emitted marker header/JSON error body before honoring a 4xx as permanent, and treat a bare/HTML 4xx as retryable); (b) bound rather than abandon — retry 4xx with the same backoff up to a long ceiling; (c) at minimum, make the abandonment loud on the *controller* side too, since today the only trace is a single ERROR line in the agent's own log.
- **See also — W1-6 forward reference:** the addendum probe above has pre-executed the generic half of W1-6 (`docs/superpowers/specs/2026-07-29-edge-case-testing-design.md:79`, "Agent credential revocation while its run executes: 4xx-permanent report abandonment vs run reap"). Both hit the identical `if` at `retry.go:34`, but the two 4xx sources are not the same class: W1-6 Part B's 401 is a **legitimately** permanent controller-originated rejection (the agent's credential really is revoked; retrying forever would be pointless), whereas this entry's 403 is an **illegitimate** intermediary-originated 403 (nginx's IP deny, not the controller saying "give up") — the same abandonment code path, triggered for opposite reasons. When W1-6 is run, triage its Part B result against this distinction rather than re-deriving the `retry.go:34` mechanism from scratch.

  --------------------------------------+------------+-----------+-----------+-----------+-------------------------------+-----------
   94268ad8-50f7-4c27-b49b-454abaf49283 |          0 | append    | Running   |           | 2026-07-29 12:03:29.711167+00 |
   eb130ec5-2c15-4f05-91ec-e2834cf383c9 |          0 | probe     | Succeeded |         0 | 2026-07-29 12:05:09.935462+00 | 2026-07-29 12:05:09.945831+00
   4be51a4f-c1b8-4111-920c-a8029cec71cb |          0 | quick     | Running   |           | 2026-07-29 12:09:18.730681+00 |
  ```
  while the corresponding `runs` rows read `Failed` (`94268ad8` at `12:04:48.850844+00`, `4be51a4f` at `12:10:31.733876+00`). Both step rows still carry `status='Running'`, `exit_code=NULL`, `ended_at=NULL`, indefinitely — nothing in the system ever revisits them. Two independent code paths guarantee this outcome, so it is not a race:
  - `FinishRun` (`internal/store/postgres.go:747-782`), the single funnel used by `MarkRunFinished` and therefore by both `failOrphanedRun` callers, updates `runs`, then `DELETE FROM mutex_holders WHERE run_id = $1`, then `UPDATE named_lock_slots ... WHERE run_id = $1`, and **nothing else** — `step_reports` is never touched.
  - Even a late step report cannot repair it: `handleAgentReportStep` (`internal/controller/api_agent.go:513-525`) `GetRun`s first and, for a `Succeeded`/`Failed`/`Cancelled` run, returns `200 {"alreadyFinalized":true}` **without** calling `UpsertStepReport` — deliberately, so a stale report cannot write step state inconsistent with a terminal run. The side effect is that the pre-existing `Running` row, which is *equally* inconsistent, is the one that survives.
- **Expected:** Per I7, run status and the rows that describe it must not contradict each other or reality. A `Failed` run whose only step is displayed as still `Running`, with no end time, contradicts both: nothing is executing, and the run is over.
- **Notes:** Rated **minor**, not major, on this file's own rubric: the authoritative run status is correct, no lock is leaked (`mutex_holders`/`named_lock_slots` were both `(0 rows)` — see the I2/I3 entry below), nothing schedules or re-runs off the stale row, and no data is lost. It is a display/audit-row inconsistency under an already-correct terminal status — real and permanent, hence recorded as a violation rather than an observation, but low impact. Worth noting it is *systemic* rather than partition-specific: every orphan-fail path (stuck-run reaper, heartbeat reconcile, agent restart-with-same-ID reconcile, `call:` cascade cancel) goes through `failOrphanedRun` -> `MarkRunFinished` -> `FinishRun`, so any reaped run in any deployment leaves this row behind. Cheap fix: in the same `FinishRun` transaction, `UPDATE step_reports SET status = <run status>, ended_at = NOW() WHERE run_id = $1 AND status = 'Running'` — it is already a transaction, and the reaper already pays the per-run cost precisely so lock release can be done per-run.

Everything above about reap timing, mutex release, side-effect accounting and zombie duration is unaffected by that difference (the reaper only reads `last_seen_at`, which stops advancing either way). What *is* affected is agent-side error classification — and that difference is the whole subject of the major entry above.

The cost matters most in exactly the situation this scenario probes: after `revoke-credentials`, the identity read is the operator's only per-identity view, and it shows `status: "active"` with no `disabledAt` and no `lastAuthenticatedAt` — nothing whatsoever indicating that every credential for that identity was revoked minutes earlier. Cheapest fix: set `last_authenticated_at = NOW()` alongside the existing `TouchAgentCredential` write, which is already rate-limited by `s.credentialTouches.shouldTouch` and so adds no new per-request cost; or drop the field from the API and the schema if it is not wanted. A second, larger option worth the operator's consideration: surface credential state on the identity read (e.g. an active-credential count or a `credentialsRevokedAt`), so that `revoke-credentials` — which `docs/troubleshooting.md:1084-1088` prescribes as the response to a *lost or replayed refresh credential*, i.e. a security incident — leaves a visible trace on the object an operator would actually inspect.

## W1-6 — observation: a de-credentialled agent becomes a permanent, un-backed-off rejection generator — ~8.2 ERROR log lines/s on the agent, and a controller-side rejected-auth load that *rises* from an ~8.3/s steady floor to a derived ~67/s peak (20,447 total, averaging ~30.6/s across the outage), until a human stops the process
- **Invariant:** I5 (bounded recovery — the agent never recovers and never backs off)
- **Severity:** minor (observation — no invariant violated and no documented promise broken; recorded for the numbers and the fleet-scale extrapolation)
- **Repro:** `test/edgecase/scenarios/w1-6-credential-revocation.md`, Parts A-C, measured over the two de-credentialled windows: `agent2` from `revoked_at 12:45:53.838Z` to its restart-exit `12:53:25.558Z` (451.7s) and `agent1` from `disabled_at 12:55:07.144Z` to its restart-exit `12:58:43.513Z` (216.4s). Raw evidence: `w1-6/derived-counts.txt`, `w1-6/metrics.txt`, `w1-6/agent1-full.log`, `w1-6/agent2-full.log`, `w1-6/audit.txt`, `w1-6/db-final.txt`.
- **Observed:**
  - **Agent-side log firehose.** `agent2` emitted **3483** `ERROR`-level `"msg":"claim"` lines between `12:46:21.858015814Z` and `12:53:24.666509128Z` (422.8s) — **8.24 lines/s** — out of 3486 ERROR lines total; `agent1` emitted **1600** such lines between `12:55:22.695235118Z` and `12:58:41.074910422Z` (198.4s) — **8.07 lines/s** — out of 1601 (`w1-6/derived-counts.txt`; the two rates are derived by dividing those logged counts by those logged first-to-last spans). The mechanism is the same one W1-5 recorded at 8.2 lines/s under partition: 16 detached claim slots each retrying every ~2s, each logging its rejection at `ERROR`. The two lines that actually matter — the `"permanent error, giving up retry"` pair marking the abandoned step/finish report — sit inside that stream at the same severity. Everything else in both logs is nearly silent by comparison: 3 and 4 `INFO` lines respectively, plus the 15s-cadence heartbeat failures (30 and 14) and 5s-cadence cancel-poll failures (53 and 43) at `WARN`.
  - **Controller-side rejected-auth load, corrected: this is not a flat rate, it is a rising curve, and claim slots are not its dominant term.** `unifiedcd_agent_auth_events_total{provider="access",reason="invalid",result="failure"}` read **6812 / 6809 / 6826** on `controller1` / `controller2` / `controller3` at `13:02:41Z` (`w1-6/metrics.txt`) = **20,447** rejections (measured), against **689** successes over the whole ~20-minute stack lifetime. Dividing that total by the two windows' combined span (668.1s) gives **~30.6 rejected requests/s** (20447 / 668.1, derived) — that number is correct as an *average*, but it is not a rate anything in the system actually ran at: the true shape is dominated by `LogPusher.flushLocked` (`internal/agent/runner.go:358-366`) re-sending **every** still-pending batch as its own `AppendLogBulk` call on each 2s auto-flush tick (`logPusherAutoFlushEvery`, `runner.go:211`), so request count at tick *k* of a sustained outage is *k*, not 1 — cumulative volume grows as a triangular number, quadratic in outage duration, not linear. Reconciliation model (labelled a **model**, not a second measurement, since it is built from a mix of measured and derived inputs — see the breakdown entry directly below for the full arithmetic and the command-level verification): agent2's step kept emitting output for **269.4s** past `revoked_at` before ending naturally, agent1's for **214.4s** past `disabled_at` before being terminated by the Part C restart — at ~134 and ~107 completed 2s ticks respectively, the triangular sums are ≈9,045 and ≈5,778 log-push requests; add the 5,083 measured claim-ERROR lines, ~140 measured heartbeat/cancel-poll failures, and ≈400 (derived) from agent2's 3 exit-time `Flush` retries (`runner.go:335-353`) each re-offering its ~134 still-pending batches (agent1's shutdown was cut short by the container restart before its own exit-time retries could run, so it is assumed to contribute none — the SIGTERM-to-restart gap was ~1.65s against `Flush`'s 1s retry sleep, so one pass could in fact have run; this is the model's one unhedged input, and it moves the total by at most ~1 tick's worth of batches) — **total ≈20,448, against the measured 20,447** (off by 1). That close a fit is strong corroboration the mechanism is right, treated as such and no more.
    - **Peak (derived, not measured directly): ~67 req/s**, at the single 2s tick immediately before agent2's step ended (134 requests / 2s = 67/s) — entirely from log-push retries, not from claims.
    - **Steady state once a step's output stops and nothing is left to re-flush (derived): ~8.3 req/s** — 16 detached claim slots retried every ~2s (≈8.0/s) plus the 15s-cadence heartbeat (≈0.07/s) plus the 5s-cadence cancel-poll (≈0.2/s). This is the number that actually persists indefinitely (see the corrected fleet projection below); the previous version of this entry's ~30/s figure overstated that floor by roughly 4x by treating the whole-outage average as if it were the ongoing rate, while simultaneously understating the transient peak by roughly 2x.
    - The quadratic amplification itself — not the specific 20,447 figure — is the generalizable result and is filed as its own observation entry immediately below, cross-referenced against the F9 and W1-2 spill-adjacent findings.
  - **Each rejection is a database round trip.** `agentAuth` calls `s.store.GetAgentCredentialForAuth(r.Context(), parsed.ID)` (`internal/controller/agent_auth.go:62`) *before* it can know the credential is revoked, and there is no negative cache and no short-circuit — so the bulk of the load above is also that many Postgres `SELECT`s of pure waste, at whatever the instantaneous rate is (rising from ~8.3/s to a ~67/s peak, not a flat ~30/s). This linkage is read from the code path, **not** separately measured (no per-query metric was captured).
  - **The agent never backs off and never re-authenticates.** Its claim loop retries on the same ~2s cadence for the entire window with no escalation, and — unlike the report path, where `retryUntilSuccess` abandons on a 4xx (`internal/agent/retry.go:33-37`) — nothing in the claim/heartbeat/poll loops treats a `401` as terminal. There is also no re-authentication attempt: `Client.do`'s 401 handler invalidates the token source and replays, but only for `GET`s and only if the source implements the unexported `invalidatingTokenSource` (`internal/agent/client.go:37-42`, `:96-105`), and `*CredentialManager` does not implement `Invalidate()` (`grep -rn "Invalidate()" internal/agent` matches only `client.go` and `client_test.go`'s fake), so that branch is dead for the real agent. Confirmed live: neither agent log contains any refresh attempt between revocation and restart, and the only credential-path calls in the entire audit table are the two restart pairs (`w1-6/audit.txt`). The state is therefore stable-but-useless until a human intervenes.
- **Expected:** Nothing documents a backoff obligation for the claim/heartbeat loops, and failing closed on every request is the correct security posture, so no contract is broken. I5's "bounded recovery" concerns returning to steady state after a fault, and this fault is *intentional and permanent* — there is no recovery to be bounded, which is why this is recorded as an observation rather than an I5 violation.
- **Notes:** The number the operator needs is the fleet-scale one, and it is an **extrapolation from the single-agent measurement above, not measured** — and it now has two components rather than one flat rate. The part that persists **indefinitely**, per stuck agent, until a human intervenes: roughly `N x 8.3` rejected authenticated requests/s (and equally `N x 8.3` wasted Postgres queries/s) plus `N x 8.2` ERROR log lines/s — at the ~100-agent scale named in the campaign spec's scope section that is ~830/s of steady-state waste, not the ~3,000/s previously projected from the flat ~30/s misreading. The part that is **transient but can spike far higher**: for as long as any of those N agents has a step still actively producing output during the outage, that agent's log-push contribution alone can reach the ~67/s peak measured here, and — per the amplification entry below — keeps climbing for as long as the step keeps producing output, growing quadratically with how long the step's tail sits unflushed. Two cheap mitigations, in increasing cost, both aimed at the steady floor: (a) apply the existing exponential backoff to sustained `401`s in the agent's claim/heartbeat loops and log at a decaying rate (a revoked agent has nothing useful to do; polling every 2s serves no purpose); (b) add a short negative cache for rejected credential IDs in `agentAuth` so repeated presentations of a known-revoked token do not each cost a query. Neither changes the security posture, since the authoritative check still runs on every cache miss and on every successful auth. The transient peak needs a different fix — see the amplification entry below. Also worth carrying into W6 planning: this is the same log-firehose shape W1-5 measured under partition, but there it was self-limiting (the partition heals, the agent recovers); under revocation the steady floor is unbounded in time — so if a scale/abuse scenario wants a cheap, sustained source of controller auth load, revoking a live agent is it, and pairing that with a chatty still-running step is worse still.

## W1-6 — observation: `LogPusher`'s failed-flush retry re-sends the *entire* accumulated backlog on every 2s tick, so a chatty step under a long outage drives controller request count as O(t²) in outage duration, not O(t)
- **Invariant:** I5 (bounded recovery — resource cost under an ongoing fault) — adjacent, not yet shown to violate a documented bound.
- **Severity:** minor (observation — the mechanism is code-confirmed and the model reconciles almost exactly against measurement, but nothing in `docs/` bounds retry request volume during an outage, so this does not contradict an invariant or a documented contract; recorded for the shape, which is new information, not for a broken promise)
- **Repro:** Same as the entry directly above — `test/edgecase/scenarios/w1-6-credential-revocation.md`, Parts A-C. Raw evidence: `w1-6/derived-counts.txt`, `w1-6/metrics.txt`, `w1-6/agent1-full.log`, `w1-6/agent2-full.log`. Source: `internal/agent/runner.go:207-366`.
- **Observed:**
  - **Mechanism, code-confirmed.** `flushCompleteLinesLocked` (`runner.go:291-305`) fires every `logPusherAutoFlushEvery = 2 * time.Second` (`runner.go:211`) and calls `flushLocked` (`runner.go:358-366`), which does not send only the newest data — it iterates `p.pending` and re-issues a full `AppendLogBulk` HTTP call for **every** batch still sitting there, appending the current buffer as one more batch on top. Nothing in this scenario ever recovers (the credential is permanently revoked), so no batch is ever removed from `p.pending` by success; each tick both resends every prior batch *and* adds a new one. At tick *k* since the outage began, that single tick therefore costs *k* requests, and the running total after *k* ticks is the triangular number *k(k+1)/2* — quadratic in elapsed outage time, not linear. `p.pending`'s only cap is `maxPendingBytes: 1 << 20` (1MiB, `runner.go:256`), a **byte** budget, not a batch-count budget; this scenario's batches are a few hundred bytes each (`tick N` lines), so hundreds of them fit in 1MiB and the drop-oldest/marker eviction path (`runner.go:431` onward) never engages — confirmed live, `grep -rc "dropped"` across every captured log/evidence file for this whole scenario returns **0**.
  - **Reconciliation against the measured total (model, not a second measurement — inputs individually marked below).** Outage-to-step-end/termination spans: agent2 `12:50:23.195Z - revoked_at 12:45:53.838417Z` = **269.4s** (measured, both endpoints from `w1-6/agent2-full.log` and `w1-6/db-partA.txt`); agent1 `12:58:41.549108Z - disabled_at 12:55:07.144433Z` = **214.4s** (measured, from `w1-6/partC-evidence.txt` and `w1-6/partC-live.txt`). At the 2s tick cadence that is **134** and **107** complete ticks (derived: `floor(span/2)`), giving triangular sums **9,045** and **5,778** log-push requests (derived arithmetic). Add the **5,083** measured claim-ERROR lines (3,483 + 1,600, `w1-6/derived-counts.txt`), the **140** measured heartbeat+cancel-poll failures (83 + 57, same source), and **≈400** (derived) from agent2's 3 exit-time `Flush` retries (`runner.go:335-353`) each re-offering its ~134 still-pending batches — sum **≈20,448**, against the **20,447** measured on the controllers (`w1-6/metrics.txt`), a difference of **1**. Treated as strong corroboration of the mechanism, not as independent proof; the model has enough free parameters (exact tick alignment, the exit-retry count) that an exact match would be somewhat suspicious, and a difference of 1 out of ~20,000 is well inside that slack.
  - **Shape, not just volume.** The same total volume delivered at a flat rate (a hypothetical "N requests spread evenly over the outage") would be a materially different, and much less interesting, finding than what actually happens: the rate itself climbs — derived **~67 req/s** at the last tick before agent2's step ended (134 requests in the final 2s tick alone) — because the mechanism is self-reinforcing: every tick that fails adds to what every subsequent tick has to resend.
- **Expected:** Nothing in `docs/` bounds retry request volume or rate during a controller-unreachable window — the documented contract (`docs/troubleshooting.md`, `docs/high-availability.md`) covers eventual delivery and the 1MiB drop-marker behavior, not request-count shape. I5's "bounded recovery" is about returning to steady state after a fault ends, which is a different property from "resource cost while the fault is ongoing." Recorded as an observation because it is new information about a risk, not because any invariant or contract was found to be violated by it.
- **Notes:** The result worth carrying into W6 is the amplification shape itself, not the scenario-specific 20,447 figure: **any** step that keeps producing output (however slowly) while its `LogPusher` cannot reach the controller — whether the cause is a permanent revocation (this scenario), a genuine transient 5xx outage (W1-1, W1-2), or an intermediary 4xx (W1-5) — pays a request cost that grows quadratically with how long that condition overlaps the step's remaining runtime, because `flushLocked` resends the whole backlog rather than just the newest batch. W1-1's outage (`FINDINGS.md` above, ~81s against a light `tick`-line load) never demonstrated this because the outage started and ended entirely before the step's natural completion, giving the 2s ticker many chances to drain `pending` well before the step-end `Flush` ever ran — so the quadratic shape was present in principle there too but never got the chance to compound. This scenario's ~269s/~214s spans are what exposed it. **Cross-references, not re-filings:** this sits in the same `LogPusher`/`p.pending` machinery as two already-filed items but is a distinct failure/cost shape from both — the prior agent-failsafe audit's **F9** finding (`unified-cd-audit-findings` memory: "agent LogPusher 1MiB silent drop") is about **data loss at the byte cap**, which this scenario's small batches never approached; the **W1-2 major I4** finding above ("Postgres outage overlapping a step's natural completion silently and permanently drops the tail...") is about **data loss under the bounded 5s step-end retry budget**, which this scenario also reproduced (see the log-loss bullets in the entries above) but is mechanistically the *exit* of the same retry loop this entry is about, not its steady-state cost. This entry adds a third, non-overlapping shape: **no data is lost *by this mechanism*** (every batch keeps being retried, confirmed by the `grep -rc "dropped"` = 0 result above; the 266 + ~214 lines this scenario did lose went to the step-end exit path — the W1-2 major — not to the retry loop described here) — the cost is pure wasted request/query volume, growing without bound as long as the step keeps producing and the outage keeps going. Cheapest fix, in the same spirit as F9/W1-2's recommendations: have `flushLocked` send at most the newest batch per tick (or coalesce all pending batches into a single `AppendLogBulk` call) instead of one HTTP request per historically-accumulated batch — this would flatten the shape to O(t) with no change to eventual-delivery semantics or to the (separately-filed) step-end data-loss behavior.

- **3. Measured and derived here: 20,447 rejections measured controller-side against a model reconciling to ~20,448, a derived **~67 req/s** peak at the last tick before the step ended, against a derived **~8.3 req/s** floor once nothing is left to re-flush. **W6-S2 (log/NOTIFY hotspot) picks this up** — it is already the scenario chartered to measure log throughput and `LogPusher` behavior under sustained load/partition, and the amplification is a per-agent multiplier on exactly that load. Keep the three `LogPusher` items distinct when triaging: **F9** is data loss at the 1MiB byte cap (never approached in W1); the **W1-2 major** is data loss at the bounded 5s step-end retry exit; **this** is pure wasted request/query volume with no data loss by its own mechanism.

### Forward questions answered

- **(a) Does W1's reaper/lock-release behavior change W2-3's boundary-timing plan? Yes, in three concrete ways.** W2-3 as specified (`docs/superpowers/specs/2026-07-29-edge-case-testing-design.md:88`) is "stuck-run reaper boundary timing: heartbeat staleness straddling 90s, claims straddling the 60s grace; lock release on reap".
  1. **The 90s boundary is not observable through wall-clock reap timing at compose level — plan W2-3 as a Level-1 deterministic probe, not a timing race.** W1 observed three real reaps against the documented `staleAfter` 90s + interval 30s: **+92.3s** (W1-5 main probe), **+94.1s** (W1-6 Part C) and **+108.9s** (W1-6 Part A), each stated relative to that run's last successful heartbeat. **The three anchors are not equally solid, which matters because this argument turns on the spread.** W1-6's two are measured: `lastSeenAt` was read directly from `GET /api/v1/agents` and froze at `12:55:06.860418Z` (Part C) and `12:45:51.831889Z` (Part A). W1-5's `12:03:16.55Z` is **inferred**, not measured — a successful heartbeat logs nothing, so it was extrapolated backwards one 15s interval from the first *failing* heartbeat, and independently bounded by the reaper's own predicate (which at reap time required `last_seen_at < 12:03:18.86Z`); the entry itself says so. The inference is sound and its error is at most a fraction of a heartbeat interval, but it is a derived anchor sitting inside a ~16.6s spread, so a W2-3 author must not treat that spread as three clean measurements. Read that way, all three are inside the contract and the spread is best explained as reaper-tick phase — where the staleness crossing happens to land within the 30s tick. A scenario trying to discriminate "heartbeat staleness at 89s vs 91s" by watching wall-clock reaps would be reading a signal roughly a third the size of its own noise. The spec already lists W2-3 in the Level-1 class (`...design.md:225`); W1's numbers convert that from a preference into a requirement — drive `ListStuckRunIDs` directly with constructed `last_seen_at`/`claimed_at` values, exactly as W0-2 drove `checkAndFireSchedules`, and keep compose only for an end-to-end sanity arm.
  2. **W2-3 must treat orphan-failing as *two* mechanisms with different clocks, and must state which one each arm tests.** W1-5's addendum failed a run through the **heartbeat reconcile** (`internal/controller/api_agent.go:99-124`, `heartbeatReconcileGrace` 60s from `claimed_at`), *not* the stuck-run reaper — and the reason is a boundary behavior W2-3 will hit head-on. Stated with the right causal emphasis: **that partition was 53.0s long against a 90s `staleAfter`, so `ListStuckRunIDs`'s `a.last_seen_at < NOW() - staleAfter` conjunct (`internal/store/postgres.go:1224`) never matched on any tick** — the reaper was never in play, rather than having been kicked out of play by the heal. The 60s claim grace did expire (`claimed_at`+60s = `12:10:18.72Z`) and the reconcile then failed the run at `12:10:31.73Z`, only **13.0s** later — so the grace boundary was not "long since" crossed by the time the run settled; the two events are adjacent, and it is the reconcile's clock, not the reaper's, that produced the outcome. **The inferred generalization (code inference, not a measurement, and not unconditional): a successful heartbeat that keeps `last_seen_at` fresher than `staleAfter` keeps the run out of the reaper's candidate set — but only while the agent row still exists and stays fresh.** The predicate is `(a.id IS NULL OR a.last_seen_at < NOW() - staleAfter)` over a `LEFT JOIN agents`, so once the background sweep `DeleteStaleAgents(ctx, 5*time.Minute)` (`cmd/controller/main.go:390`, `internal/store/postgres.go:1203`) removes the agent row, `a.id IS NULL` satisfies the conjunct on its own and the run becomes reapable again. W1-6 observed that deletion happening (`agent2` gone from `agents` ~5 min after its last heartbeat) though not its reaper consequence. W2-3 should treat the "one heartbeat immunizes the run" rule as holding on a 5-minute horizon, not permanently, and should verify it rather than inherit it. So: any W2-3 arm that intends to test the reaper must hold the agent stale for the *whole* window (revocation, per W1-6, does this unconditionally and is the cleaner instrument; a healable partition does not), and any arm that lets the agent recover is testing the reconcile path instead. The discriminator is cheap and W1 validated it — the reaper logs a `WARN "stuck-run reaper: failed orphaned run (agent lost)"` naming the `runId`, whereas the reconcile path logs nothing and is identified by `runs.updated_at` matching the agent's first post-grace heartbeat (matched to ~30ms in W1-5's addendum).
  3. **The "lock release on reap" limb is already answered end-to-end; downgrade it to a boundary re-check and spend the budget on 1 and 2.** W1-5 confirmed `FinishRun` performs `DELETE FROM mutex_holders` in the same transaction as the status flip (`internal/store/postgres.go:768-770`) and demonstrated the consequence live: a successor acquired the mutex and went Queued-to-Succeeded in **732ms**, with `mutex_holders` and `named_lock_slots` both `(0 rows)` on direct inspection. Because it is one transaction, there is no boundary for a timing scenario to straddle — the interesting residual is not leakage but *physical overlap*, which W1-5 also measured (the successor acquired, ran and finished while the zombie was demonstrably still appending side effects, and the zombie went on appending until its own loop ran out) and which W2-3 cannot improve on without fencing tokens that do not exist. Recommend W2-3 keep a single cheap assertion here and drop the timing arm.
- **(b) Does the nginx-block tooling suffice for W2's partition needs? Yes — W2 does not need a real packet-level partition, and no Dockerfile/`NET_ADMIN` work should be scheduled for it.** W1-5 established the precise scope of the tool: because unified-cd's agent protocol is strictly agent-polls-controller (claim, heartbeat, log push, step/finish report and cancel poll are all agent-initiated; the controller never dials the agent), an nginx per-agent IP deny is **equivalent to a one-way partition in what the agent can accomplish**, and everything W2 keys on — `last_seen_at` ceasing to advance, claims aging past their grace, locks releasing on reap, a replacement agent re-registering under the same ID — depends only on that. It is **not equivalent in what the agent observes**: the agent sees prompt `403`s rather than a TCP black-hole of connect timeouts and half-open sockets, and that single difference is what produced the W1-5 major (a transport error is not an `HTTPError` and would have been retried normally). Checked against each W2 scenario: W2-1, W2-5, W2-6, W2-7, W2-8 and W2-9 need no partition at all (W2-7 in particular is two *live* agents sharing one ID, not an unreachable one); W2-2, W2-3 and W2-4 need only "the agent cannot reach the controller", which nginx-block delivers exactly — and for W2-2 and W2-4 a plain `kill-hard` on the agent is an equally valid instrument. **The one thing W2 must do is not read agent-side error classification, or a terminal status derived from a 4xx, as a result** — under nginx-block those are contaminated by the known artifact, and any W2 run that settles `Failed` via report abandonment should be attributed to the W1-5 major rather than re-filed. Two further notes for whoever eventually does need transport-level failure (a fix-verification pass on the W1-5 major, or a W6 abuse scenario): `test/edgecase/tools/inject.sh` **already ships `partition`/`heal`**, implemented as `docker network disconnect/connect`, which produces DNS/dial failures rather than HTTP status codes and needs no container capability — it is a full disconnect rather than a one-way block, but for a strictly agent-polls-controller protocol the two are indistinguishable in controller-visible state. It was **not exercised anywhere in W1**, so it is unvalidated, and validating it is a cheap prerequisite for that future work — not for W2.
