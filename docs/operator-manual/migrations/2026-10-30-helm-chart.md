# Migrating: Kustomize overlays replaced by a Helm chart

Kubernetes installs now come from a Helm chart, `charts/unified-cd`, published
to `oci://ghcr.io/eirueimi/charts/unified-cd`. The Kustomize overlays under
`manifests/` (`base`, `install`, `core-install`, `agent-only`) are removed, so
`kubectl apply -k manifests/install` and `kubectl kustomize manifests/...` no
longer work from a checkout. The release assets `install.yaml`,
`core-install.yaml` and `agent-only.yaml` still exist and are rendered from the
chart; you can keep applying them.

**You are affected only if** you applied or built on the overlays from a
checkout (`kubectl apply -k`, a Kustomization that lists
`github.com/eirueimi/unified-cd//manifests/...` as a base, or a patch against
the overlay files). If you apply the release `install.yaml`, `core-install.yaml`
or `agent-only.yaml`, re-applying the new bundle over a v0.11.0 install works in
place (CI tests this) and never replaces the KEK. One leftover needs a manual
cleanup: the Garage ConfigMap. v0.11.0 created it as `garage-config-<hash>`; the
new bundle creates a plain `garage-config` and the hashed one is orphaned. After
the Garage Pod has restarted on the new ConfigMap, delete it:

```bash
kubectl -n unified-cd get configmap -o name | grep '^configmap/garage-config-' \
  | xargs -r kubectl -n unified-cd delete
```

## What changed

| Before | After |
|---|---|
| `kubectl apply -k manifests/install` | `helm install unified-cd charts/unified-cd -n unified-cd --create-namespace` (or the OCI chart; see [Installation](../../getting-started/installation.md#kubernetes)) |
| `kubectl apply -k manifests/core-install` | `helm install ... --set bundledStores.enabled=false --set controller.existingSecret=unified-cd-controller --set agent.server=https://...` |
| `kubectl apply -k manifests/agent-only` | `helm install ... --set controller.enabled=false --set bundledStores.enabled=false --set agent.server=https://...` |
| `kubectl kustomize manifests/<overlay>` | `helm template unified-cd charts/unified-cd -n unified-cd ...` |
| `make manifests` rendered the bundles with `kubectl kustomize` | It needs `helm` instead and produces the same three files. |
| Everything lived in the hard-coded `unified-cd` namespace | The release namespace (`-n`). The `unified-cd` default of the bundles is unchanged. |
| A copy of the overlay and a patch per customization | One values file. |

Resource names are unchanged and are not prefixed with the release name
(`unified-cd-controller`, `unified-cd-controller-config`,
`unified-cd-controller-kek`, `unified-cd-k8s-agent`, `postgres`, `garage`, the
`ci` namespace, and so on), so existing installs line up with the chart. For the
same reason, only one controller release can exist per cluster: the
`unified-cd-controller-kubernetes-enrollment` ClusterRole and ClusterRoleBinding
have fixed cluster-scoped names, and the default job namespace `ci` is
cluster-wide too. A second release, for example an agent-only one, must set a
different `jobNamespace.name`; a second controller is blocked by the
cluster-scoped RBAC names.

## Overlay customization to chart values

| In the overlay | Chart values |
|---|---|
| Choose `install` / `core-install` / `agent-only` | `bundledStores.enabled`, `controller.enabled`, `agent.enabled` (see the three commands above) |
| `images:` / `newTag` for the controller or agent | `controller.image.tag`, `agent.image.tag` (default: the chart's `appVersion`) and `.image.repository` |
| `replicas` patch | `controller.replicas`, `agent.replicas` |
| `resources` patch | `controller.resources`, `agent.resources` |
| Node selector, tolerations, affinity patches | `controller.nodeSelector` / `tolerations` / `affinity`, and the same under `agent` |
| `controller-config-patch.yaml`, `config-configmap.yaml` edits | `controller.config` (deep-merged over the chart's defaults) |
| `agent-config-patch.yaml`, `k8s-agent` config edits | `agent.config` (deep-merged) |
| `server:` URL in the agent config (replacing `https://controller.example.invalid`) | `agent.server` (must be `https://`; empty means the in-cluster Service over plain HTTP with `allowInsecureHTTP: true`, which applies whenever the controller is installed, not only in trial mode; NOTES prints a warning when `bundledStores.enabled=false`) |
| `secret.yaml` (trial credentials) or your own `unified-cd-controller` Secret | Trial: the default. Your own: `controller.existingSecret` with `bundledStores.enabled=false` |
| The `unified-cd-controller-kek` Secret | Unchanged; name it with `controller.kek.secretName`. Generated by the KEK Job with the bundled stores, otherwise create it yourself |
| `kek-job.yaml` | `controller.kek.generate`, `controller.kek.job.image`, `controller.kek.job.helmHook` |
| `base/namespace/namespace.yaml` (the `ci` namespace and its Pod Security labels) | `jobNamespace.create`, `jobNamespace.name`, `jobNamespace.podSecurity.enforce` / `.audit` |
| PostgreSQL / Garage PVC size or StorageClass patches | `bundledStores.postgres.storage` / `.storageClassName`, `bundledStores.garage.storage` / `.storageClassName`; images in `bundledStores.*.image` |
| An Ingress you wrote yourself | `ingress.enabled`, `className`, `annotations`, `hosts`, `tls` |
| Service type or port | `controller.service.type`, `controller.service.port` |

The full list, with defaults, is the chart's
[values reference](https://github.com/eirueimi/unified-cd/blob/main/charts/unified-cd/README.md#values).
Config you set under `controller.config` and `agent.config` is merged key by key
over the defaults; a list you provide (for example
`agentAuth.kubernetesEnrollmentPolicies`) replaces the default list entirely.

## What you must do

### Trial installs: install fresh (recommended)

The trial stores hold development data and development credentials. Remove the
old install and install the chart:

```bash
kubectl delete -f install.yaml        # or: the release asset you applied
helm install unified-cd oci://ghcr.io/eirueimi/charts/unified-cd \
  --version <x.y.z> -n unified-cd --create-namespace
```

The bundle starts with the `unified-cd` Namespace, so deleting it removes the
whole namespace: the PostgreSQL and Garage data, the trial Secret **and the
`unified-cd-controller-kek` Secret**, plus the `ci` namespace and any job Pods in
it. Wait for the namespaces to finish terminating before running
`helm install`. If you want to keep your data, adopt the install instead (next
section).

### Existing installs: adopt the objects into a Helm release

Use this to keep data and the KEK. Helm refuses to take over an object it did
not create unless the object carries the labels and annotations below, so each
object the chart renders needs them. Do this with the same chart version that
matches the images you run, and read the rendered diff first with
`helm template`.

1. Delete the completed KEK Job and the three objects it uses. A Job's spec is
   immutable, and the chart recreates all four as a Helm hook. This does **not**
   touch the `unified-cd-controller-kek` Secret, which needs no adoption (the
   chart never owns it):

   ```bash
   kubectl -n unified-cd delete job,serviceaccount,role,rolebinding unified-cd-kek-init
   ```

2. Label and annotate every other object the chart renders. For the trial layout
   (`install.yaml`) in namespace `unified-cd`:

   ```bash
   adopt() { # adopt <namespace|-> <kind> <name>
     local ns=(-n "$1"); [ "$1" = "-" ] && ns=()
     kubectl "${ns[@]}" label --overwrite "$2" "$3" app.kubernetes.io/managed-by=Helm
     kubectl "${ns[@]}" annotate --overwrite "$2" "$3" \
       meta.helm.sh/release-name=unified-cd \
       meta.helm.sh/release-namespace=unified-cd
   }

   for o in deployment/unified-cd-controller deployment/unified-cd-k8s-agent \
            deployment/postgres deployment/garage \
            service/unified-cd-controller service/postgres service/garage \
            configmap/unified-cd-controller-config configmap/unified-cd-k8s-agent-config \
            secret/unified-cd-controller \
            serviceaccount/unified-cd-controller serviceaccount/unified-cd-k8s-agent \
            role/unified-cd-controller-kubernetes-enrollment \
            rolebinding/unified-cd-controller-kubernetes-enrollment \
            persistentvolumeclaim/postgres-data persistentvolumeclaim/garage-data; do
     adopt unified-cd "${o%%/*}" "${o#*/}"
   done
   adopt - clusterrole unified-cd-controller-kubernetes-enrollment
   adopt - clusterrolebinding unified-cd-controller-kubernetes-enrollment
   adopt - namespace ci
   adopt ci role unified-cd-k8s-agent
   adopt ci rolebinding unified-cd-k8s-agent
   ```

   The Garage ConfigMap is not in the list on purpose: on a kubectl install it is
   named `garage-config-<hash>`, so there is no `garage-config` to adopt (the
   chart creates it). Delete the hashed one after step 3 (see below).

   For `core-install.yaml` or `agent-only.yaml`, skip the objects that bundle
   does not contain (no `postgres`, `garage`, their ConfigMap, PVCs or Services,
   and no trial Secret; `agent-only.yaml` also has no controller objects). Use
   your release name and namespace in place of `unified-cd` if they differ. The
   release namespace `unified-cd` itself is never touched by the chart.

3. Install with values that reproduce your current install, using the table
   above. For an unmodified trial that is the defaults:

   ```bash
   helm install unified-cd oci://ghcr.io/eirueimi/charts/unified-cd \
     --version <x.y.z> -n unified-cd
   ```

   For `core-install.yaml`, add
   `--set bundledStores.enabled=false --set controller.existingSecret=unified-cd-controller --set agent.server=https://<your endpoint>`.
   Check the result with `helm -n unified-cd status unified-cd` and
   `kubectl -n unified-cd get pods`; the controller and agents roll once if the
   chart's Pod template differs from yours.

4. Delete the orphaned hashed Garage ConfigMap once the Garage Pod runs on the
   chart's `garage-config` (only for installs that had the bundled Garage):

   ```bash
   kubectl -n unified-cd get configmap -o name | grep '^configmap/garage-config-' \
     | xargs -r kubectl -n unified-cd delete
   ```

If `helm install` reports `exists and cannot be imported into the current
release`, the named object is missing the label or an annotation; add it and
retry. Helm adoption is documented here but not covered by the project's CI.

## Behavior to know afterwards

- **`helm uninstall` keeps the KEK Secret and the `ci` namespace.** Delete the KEK
  deliberately with `kubectl -n unified-cd delete secret unified-cd-controller-kek`,
  only if no stored secret needs to be read again. The trial PostgreSQL and
  Garage data is deleted with the release.
- **The chart refuses an Ingress with the trial credentials.** Set
  `controller.existingSecret` first; see
  [Installation: Production](../../getting-started/installation.md#production).
- **`helm upgrade` replaces a hand-edited object.** Changes made with
  `kubectl edit` to chart-managed objects are lost on the next upgrade. Move them
  into values, `controller.config` or `agent.config`.
