# Agent-owned named volumes — decisions taken during implementation

Date: 2026-10-20
Spec: `docs/superpowers/specs/2026-10-20-agent-named-volumes-design.md`
Plan: `docs/superpowers/plans/2026-10-20-agent-named-volumes.md`

This records every decision taken on the user's behalf while implementing the
plan, in the order it was taken. It exists because the implementation ran as
eleven delegated tasks with their own reviews, and the questions that arose
were settled as they arose rather than queued. Each entry says what was
decided, why, and what it costs if the decision turns out to be wrong — the
last part matters most, because it tells a later reader what to undo and how
expensive undoing it is.

Two entries are corrections: places where a decision's stated reasoning was
wrong and an implementer or reviewer checked it against the code and said so.
They are kept rather than edited away, because a record that hides its own
mistakes is not worth consulting.

Where a ruling replaces an earlier one, both appear. Ruling 28 replaces the
acquisition rule of Ruling 25; Ruling 37 replaces Ruling 22; Ruling 31 and
Ruling 32 move in opposite directions on the same field, in that order, and
the sequence is the point.

---

Ruling 1: Task 2 implements and unit-tests `ExpandVolumes` and `RequiredVolumes` only; its step 4 (call-site wiring that persists `required_volumes`) moves to Task 3 for the queue path and Task 4 for run creation. — Why: the plan orders the migration after Task 2, so Task 2 cannot write the column it names; the spec fixes only that expansion happens at queue time, not which task wires it. — Cost if wrong: one extra edit to `postgres.go` in Task 3 that would otherwise have been in Task 2; no behaviour change.
Ruling 2: Task 6 owns wiring the controller's claim HTTP handler to read `busyVolumes` from the new request body and pass it to `ClaimNextRun`. — Why: no task claims it; Task 6 already changes `internal/api`'s claim types and the agent client, so the two halves of the wire format land together and stay consistent. — Cost if wrong: the wiring sits in a task whose review surface is already large; if it belongs better in Task 3, moving it later is a pure relocation.
Ruling 3: Task 8's dispatch must state that `ValidateVolumes` already exists from Task 1 and is to be extended, not rewritten. — Why: a fresh implementer handed only Task 8's brief would see alias validation listed under "Modify `internal/dsl/volumes.go`" with no indication of what is there. — Cost if wrong: a duplicated validator that the task review would catch.
Ruling 4: The `spec.workspace.volume` shorthand is dropped; `mountPath: "."` is the only spelling, and `NormalizeVolumes` goes with it. — Why: verified in code that `WorkspaceConfig` is reachable only under `spec.podTemplate.workspace` (internal/dsl/types.go:543) and that `spec.native: true` is incompatible with `spec.podTemplate` (internal/dsl/parse.go:206), so the shorthand could never serve the native Unity case the spec's own example shows. The shorthand was design-time sugar nobody asked for; without it `NormalizeVolumes` is a pass-through a reviewer would flag as YAGNI. Spec §4.4 and §8 and plan Tasks 1/2/6/9 updated. — Cost if wrong: job authors write three lines instead of two; adding the shorthand later needs a new `Spec.Workspace` field and a precedence rule against `spec.volumes`.
Ruling 5: The apply-time "absolute mountPath is inside the workspace" check uses the container workspace root only; the native case is re-checked at mount time in Task 6. — Why: a host agent's workspace path is not knowable at apply time, so apply-time is the wrong place to decide it for native; Task 6 already owns native mounting and the never-clobber rule. — Cost if wrong: a native job with a colliding absolute path fails at run time rather than at apply time. Carried into Task 6's dispatch.
Ruling 6: The implementer's unlisted edits to `internal/dslschema/dslschema.go` and `cmd/docgen/main.go` are accepted as in scope. — Why: the plan's Global Constraints make the generated schema and field reference part of the task, and without the `oneOf` mapping the schema would publish `type: string` and editors would reject the `name: [a, b]` form the spec requires. — Cost if wrong: two small generator edits land in Task 1 instead of a later task; the generated output is correct either way.
Ruling 7: The ephemeral workspace is cleaned after the run as well as before; the after-run sweep is best-effort (warn, do not fail the run). — Why: before-run cleaning alone holds the previous run's output until that job's next run, which is not what emptyDir does, and the design calls the default workspace ephemeral. The before-run clean keeps the correctness guarantee, so the after-run sweep can fail harmlessly. Supersedes the earlier "clean before the run" ruling. Spec §4.1 and §6.3 and plan Task 7 updated. — Cost if wrong: one extra sweep per run; on a slow filesystem it adds to teardown time, and dropping it only returns to holding disk between runs.
Ruling 8: `cleanWorkspace` on a volume reuses the existing `containerCleanup` fallback, and the advisory usage measurement tolerates permission errors. — Why: on a host agent a `native: false` run writes into the volume as root when the runtime is rootful, exactly the case `prepareWorkspace` already has a cleanup-container path for; without it the documented escape hatch fails on the volumes that need it most. Spec §4.3 and plan Tasks 5 and 7 updated. — Cost if wrong: the fallback runs a throwaway container on a wipe that a plain RemoveAll would have handled.
Ruling 9: A volume's resolved path may not be, or sit under, a `working*` directory, and a test pins that the retention sweep cannot reach a volume. — Why: `gcWorkspaces` (internal/agent/workspace_gc.go:46) globs `wsBase/working*`, so the default `<workspaceDir>/volumes/<name>` is safe today only by the spelling of that glob; a volume deleted for being unused past `workspaceRetentionDays` would destroy the data the operator declared in order to keep it. Spec §4.3 and plan Task 5 updated. — Cost if wrong: an operator who deliberately wants a volume inside a `working*` directory must move it.
Ruling 10: A volume name that expands to the empty string is an expansion error, failing the run at queue time; Task 3 owns it, not Task 2. — Why: Task 2's functions are pure expanders that mirror ExpandConcurrency, which does not judge its output either; and an empty name could otherwise only surface as a run sitting Queued forever with a reason naming no volume, which is worse than a clear failure. The queue-time call site already has the fail-the-run pattern to reuse. Plan Task 3 updated. — Cost if wrong: a job whose volume name comes from an unset param fails instead of waiting; if waiting were preferred, moving the check is a one-line change.
Ruling 11: `RequiredVolumes` may return nil, and Task 3 is responsible for persisting `[]` rather than JSON `null` into `runs.required_volumes`. — Why: the reviewer is right that the brief said "empty slice" while the code returns nil, but nil is the idiomatic Go zero for a slice and every reader treats it as empty; the real hazard is only at the JSON boundary, which is Task 3's column with a `NOT NULL DEFAULT '[]'`. Fixing it at the boundary is one place instead of a convention every caller must remember. Plan Task 3 updated with a test. — Cost if wrong: if a later caller distinguishes nil from empty, it must say so itself.
Ruling 12: `runs.required_volumes` is written in exactly one place, `tryQueueRun` (Task 3); Task 4 reports required volumes but does not persist them. — Why: a volume name can be a template, and the params it expands from are resolved at queue time, not at run creation; Task 4's plan text said "every site that computes RequiredCaps also persists RequiredVolumes", which together with Ruling 1 would have produced two writers, one of them writing unexpanded names. Plan Task 4 updated. — Cost if wrong: a run created but never queued carries `[]` rather than its declared volumes; nothing reads the column before queueing.
Ruling 13: `ClaimNextRunDetached` keeping its old signature and passing an empty busy list is correct, not a gap. — Why: Task 1 rejects `spec.volumes` on a detached job at apply time, so a detached run's `required_volumes` is always `[]` and the volume clause is vacuous for it; adding busy tracking there would be machinery with no reachable caller. — Cost if wrong: if detached runs are ever allowed volumes, that signature and the handler must be revisited together; noted here so the search is one grep.
Ruling 14: The implementer's schema sentinel for migration 022 in `internal/store/verify.go` is accepted as in scope. — Why: `TestSchemaSentinelsCoverAllMigrations` fails without it, so the migration and the sentinel are one unit of work; this is the repository's own guard against a hand-maintained list drifting from its source, and leaving it to a later task would mean committing a red test. — Cost if wrong: one small edit lands in Task 3 rather than elsewhere.
Ruling 15: One run may name the same volume in several entries, and that stays legal; the agent reserves each distinct resolved volume ONCE per run and mounts it at every mountPath naming it. — Why: the reviewer read a requirement of [["a"],["a"]] as needing two distinct volumes, which is wrong — mounting one volume at two paths is legitimate, and Task 1 rejects duplicate mountPaths rather than duplicate names, so the claim clause is right to call it satisfiable. The real hazard is one step further on: a naive per-entry reservation would have the second entry block on a volume the SAME run already holds, deadlocking the run against itself. Reservation is therefore per (run, volume), keyed on the resolved name after deduplication. Plan Tasks 5 and 6 updated with a test. — Cost if wrong: if duplicate names prove meaningless in practice, rejecting them at apply time is a small Task 1 addition and this rule becomes dead weight.
Ruling 16: Task 4 correctly leaves api_runs.go, api_webhooks.go and scheduler.go untouched, although its brief's Files list named them. — Why: Ruling 12 made Task 4 a reporter rather than a writer, and at those three sites the spec is unexpanded and CreateRun takes no volumes, so computing RequiredVolumes there would be dead code that also risked persisting unexpanded names. The brief's Files list was stale, not the implementation. — Cost if wrong: if a future caller needs required volumes at creation time, it must expand them itself first.
Ruling 17: The unrequested additions are accepted as in scope — api.AgentInfo.Volumes with ListAgents/GetAgent reading agents.volumes, and VolumesDependOnParams. — Why: Task 3 wrote the column but nothing read it, so the comparison this task exists to perform had no input without the former; and without the latter a templated volume name would be reported as unknown before its params are even resolved, which is precisely the false alarm this task is meant to prevent. VolumesDependOnParams mirrors the existing SelectorDependsOnParams. — Cost if wrong: Task 6 must not re-add AgentInfo.Volumes; noted below.
Ruling 18: Task 6 must add a context-aware wait for a reservation; Task 5's context-free `Reserve` is not left as the only entry point. — Why: as written, a run waiting for a busy exclusive volume cannot be abandoned, so the agent's drain path (--drain-timeout, SIGTERM) would block on it, holding a slot until the holder finishes — tens of minutes for a Unity build. Operability, not polish: an agent that cannot be drained cannot be rolled. Plan Task 6 updated with the rule and a drain test. — Cost if wrong: one extra entry point on the manager; the context-free Reserve stays usable where no wait is possible.
Ruling 19: Reservations are released once at run end, not as each entry is unmounted. — Why: a re-entrant Reserve returns a no-op release, so only the call that actually took the volume frees it; releasing per entry would have the first unmount free a volume the run is still using through its second mount path. Plan Task 6 updated. — Cost if wrong: a volume stays reserved for the tail of a run's teardown, which is the safe direction.
Ruling 20: Task 5's additions beyond the brief are accepted — CheckUsage, the mode constants, Agent.Volumes, refusing a relative explicit path, refusing a path that equals or contains the workspace dir, refusing overlapping volume paths, and ReservePath accepting a POSIX leading slash as absolute. — Why: each closes a way to lose data or to configure something incoherent. A volume containing the workspace would nest the workspace inside the thing it mounts; overlapping volume paths would make two names one directory with two exclusion states; and DSL mount paths are POSIX-style, so filepath.IsAbs alone would classify "/home/ci/.cache" as relative on a Windows agent. — Cost if wrong: an operator with a deliberate relative or overlapping path layout must change their config; none of these is reachable from a job.
Ruling 21: Three of Task 5's minors are load-bearing for Task 6 and move into its dispatch rather than being deferred. — Why: (a) VolumeManager's methods panic on a nil receiver while Agent.Volumes is documented as nillable, and Task 6 is the first caller on the claim and advertise path; (b) ReservePath keys on filepath.Clean, so a POSIX mount path becomes a backslash spelling on Windows and Busy() reports a string the controller cannot match; (c) the GC-reach refusal covers working* but not <base>/detached/<runID>, which the agent deletes after each run, nor <base>/.ucd-tools, which holds the shim. Each would fail first in Task 6's code or in production rather than in Task 5's tests. Plan Task 6 updated with all three. — Cost if wrong: Task 6's review surface grows by three small changes that would otherwise have been a follow-up commit.
Ruling 22: An artifact or cache path that falls inside a volume's mount point on an isolated run must FAIL the run, naming the path, the volume and the mount path. Resolving it into the volume's host directory is the proper fix and becomes a follow-up, not part of this task. — Why: host-side artifact and cache steps resolve against the host workDir, where a container-only mount point is an empty directory, so `artifacts:` archives nothing and `cache:` saves nothing while the run goes green. A user reads that as their files being saved. Silent data loss is the worst failure this feature could ship; a loud refusal is wrong-shaped but honest, and the proper resolution is a contained follow-up rather than more growth on an already 630-line file. — Cost if wrong: a job that legitimately wants an artifact from inside a volume must wait for the follow-up instead of working now.
Ruling 23: The claim request carries the agent's full volume list as well as its busy list, and `UpsertAgentOnClaim` writes volumes when the claim supplies them while still never wiping them. — Why: a row recreated by a claim otherwise stops routing volume jobs until the next registration, and the user-visible symptom is a run queued with "no agent declares volume X" while an agent in fact does — actively misleading rather than merely slow. Task 3's property that a claim-time upsert cannot wipe volumes is preserved. — Cost if wrong: the claim body grows by one field that registration also sends.
Ruling 24: The claim request body is sent unconditionally; the test servers that hung on it are the defect and get fixed. — Why: a body sent only when something is busy makes the common path and the busy path different code, which the next maintainer will not expect. The servers that hung are test doubles long-polling on r.Context() without reading the request body. If a non-test path genuinely cannot read a body, the implementer was told to stop and say so rather than revert. — Cost if wrong: if some real HTTP path cannot drain the body, the conditional send comes back, and we will know because the implementer will have said so.
Ruling 25: The candidate-set collapse is prevented, not merely logged, and the prevention lives in `reserveRunVolumes` rather than in `Reserve`. — Why: `Reserve` checks "already held by this run" before "free", so `name: [c1, c2]` at one path and `name: [c1]` at another both resolve to c1 — two independent caches silently become shared state. The brief blesses re-entrancy for the narrow case of the same volume named twice at two paths, not for merging distinct candidate sets. Logging would leave the aliasing in place; fixing it inside `Reserve` would break the legal case. The rule: prefer candidates this run has not chosen; if every unchosen candidate is busy, WAIT for one rather than fall back to one this run holds; alias only when every candidate in the set is already held by this run, which is exactly the legal case. Canonical ordering is kept so this cannot reintroduce the opposite-order interlock. — Cost if wrong: a job with overlapping candidate sets waits where it used to proceed with aliased state; the wait is visible and the aliasing was not.
Ruling 26: A failed unlink of an ABSOLUTE native mount path keeps its path reservation for the process's lifetime. — Why: a relative stale link is recoverable, because the next installLink replaces a link it owns; an absolute one is machine-wide, so releasing the reservation lets a different volume's run be handed that path and silently repoint it. Asymmetric treatment is the point and must be commented. — Cost if wrong: an absolute mount path is unusable until the agent restarts, after a failure that should not happen; the alternative is silent cross-volume contamination.
Ruling 27: Two entries carrying the SAME multi-candidate list now resolve to two distinct volumes while two are free, where before both resolved to the first candidate. Accepted as a consequence of Ruling 25, not an excess. — Why: Ruling 25's rule is "prefer candidates this run has not chosen", and nothing in it distinguishes identical candidate sets from overlapping ones; an author who wanted one volume at two paths writes the same single name twice, which still aliases, while an author who writes a pool twice is most plausibly asking for two from the pool. The old behaviour was the accident. Task 10 documents it. — Cost if wrong: a job that wrote the same pool twice intending one volume now gets two, which costs disk rather than correctness, and writing the single name twice expresses the old behaviour exactly.
Ruling 28 (REPLACES the acquisition rule in Ruling 25; the aliasing prevention stands): a run acquires every volume AND every absolute native mount path it needs atomically, all or nothing, holding nothing while it waits. On failure it takes nothing, waits for a change, and retries. — Why: Ruling 25 told the implementer to acquire per entry and wait for an unchosen candidate, which is textbook hold-and-wait. Two runs each declaring [c1, c2] at two paths interlock: A takes c1, B takes c2, and each then waits for the other's. The canonical ordering cannot help because both runs sort identically, and the code comment claiming only non-equal overlaps interlock became false. I also extended the atomic unit to cover absolute paths, which the re-reviewer did not raise: a native run holding a volume while waiting for an absolute path is the same shape. The assignment search must be a complete backtracking search rather than a greedy pass, because greedy also fails the re-reviewer's [a,b] + [a,c] case, waiting where (b,a) would have satisfied both. — Cost if wrong: a run with many entries does slightly more work under the manager lock, and a run that could have proceeded with a partial acquisition now waits for all of it; the alternative is a hang with no timeout in production. MY RULING 25 CAUSED THIS DEFECT — the implementer built what it was told. Plan Task 5's per-entry Reserve interface is superseded on this point for the run-level path; Reserve itself keeps its per-run re-entrancy for other callers.
Ruling 29: The agent-wide `--clean-workspace` flag must never wipe a volume; only the job's own `spec.cleanWorkspace` or `podTemplate.cleanWorkspace` may. The flag is also now a no-op for ordinary workspaces and its help text must say so. — Why: the flag is an operator-level hygiene default set once for a fleet, and its purpose was "do not let a job inherit another run's leftovers", which Task 7's unconditional cleaning now guarantees for every ordinary workspace anyway. Applied to a volume it would destroy, on every run, the tens of gigabytes the job's own config declared as the thing to keep. An operator setting a hygiene default has not knowingly agreed to that; a job asking for cleanWorkspace has. Removing the now-pointless flag is a follow-up, not this project. — Cost if wrong: an operator who genuinely wanted a fleet-wide wipe of volume workspaces must set it per job; the alternative silently defeats the entire feature.
Ruling 30: Task 7's other five judgements are accepted as implemented. (a) `prepareWorkspace` takes `vol *volumeWorkspace` rather than a bool, because the error message and the out-of-volume marker path both need the volume name. (b) An ordinary workspace that cannot be emptied, and a reused k8s pod whose clear fails, now FAIL rather than warn-and-proceed, and the dirty pod is deleted rather than returned to the pool — once the design promises an empty workspace, starting on another run's files is worse than refusing. (c) A volume is never swept AFTER a run even with clean=true, because that would destroy exactly what the run produced. (d) Ordinary workspaces no longer carry `.ucd-mode`: the marker existed to detect a native/isolated flip carrying root-owned leftovers, and unconditional cleaning means there are none to carry. (e) The help text and docs/reference/configuration.md edits stay. — Cost if wrong: (b) turns two previously-tolerated conditions into run failures, which the migration guide must state.
Ruling 31: Spec §4.10 was wrong and is corrected: there is no `spec.cleanWorkspace`. `CleanWorkspace` exists only on `PodTemplate` (internal/dsl/types.go:542, inside the struct declared at :539); `Spec` has no such field. — Why: I wrote §4.10 from memory of an early grep that showed the field without its enclosing struct, and the Task 7 implementer verified it against the code rather than implementing a field that does not exist. The spec is the authority this plan argues from, so a false field name in it would propagate into Task 10's docs and the migration guide. §4.10 now also records that --clean-workspace is a no-op and why. — Cost if wrong: none; this is a correction to a document, verified against the type definition.
Ruling 32: Add `spec.cleanWorkspace`. — Why: the mode-flip error pointed users at `podTemplate.cleanWorkspace`, but internal/dsl/parse.go:204-207 rejects `spec.native: true` together with `spec.podTemplate`, and Ruling 29 removed the agent-wide flag as an alternative. A native job using a volume as its workspace therefore had NO way to ask for a clean — and that is exactly the configuration this project exists for, a native macOS Unity build with its checkout and Library/ on a persistent volume. The only remedy would have been an operator hand-deleting tens of gigabytes on the agent host. The field also belongs at the spec level on its merits: it is a workspace concern, `native` lives there too, and `podTemplate` is the Kubernetes-flavoured corner. My own design draft said `spec.cleanWorkspace` before the implementer correctly reported it did not exist; the instinct was right and the field was simply missing. `clean` is the OR of both spellings. Spec §4.10 updated. — Cost if wrong: one more DSL field to document and keep; the alternative leaves the primary use case with no escape hatch.
Ruling 33: Task 8's four disclosed judgements are accepted. (a) The brief's "alias yielding UNIFIED_WORKSPACE" test is unmeetable literally, because every generated name begins with UNIFIED_VOLUME_; the exact-name check stands and its test fires by temporarily reserving a name. The implementer also rejects aliases invalid in an environment variable name, which means a literal volume name containing such characters now requires `as` — a forced explicitness I accept. (b) `k8sagent.imageStepEnv` deliberately untouched, because the k8s-agent advertises no volumes yet; moved into Task 9's plan, which is the task that changes that. (c) A step's own `env:` can override UNIFIED_VOLUME_X and `post:` hooks get none of these variables, consistent with UNIFIED_WORKSPACE today. (d) A scoped `runsIn.image` step gets a DEFINED BUT EMPTY variable with no error, because its scope container has no volume mounted. — Why (d) differs from Ruling 22, where I made the analogous artifact case fail loudly: there the agent knows the path falls inside a volume mount and can detect it, whereas here it cannot know whether a step references the variable at all, so documentation is the only available lever. The distinction is detectability, not appetite for silence. — Cost if wrong: a scoped step doing `export GOCACHE="$UNIFIED_VOLUME_X/build"` gets `/build` and writes into the container, losing the data; Task 10 must document this prominently, because the spec's own GOCACHE example is exactly that shape.
CORRECTION to Ruling 33(d): the variable is left UNSET, not "defined but empty" — volumeExtraEnv(nil) returns nil and hostBackend.VolumePaths returns nil for a scoped step (backend_host.go:348-353). The reviewer verified this against the code; my earlier wording and the brief's were both loose. Unset is the better behaviour: `set -u` and `${VAR:?}` fail loudly, where an exported empty value would be treated as unset by most tools anyway, and it names no path that does not exist in the container.
Ruling 34: A volume whose agent-config name contains characters outside letters, digits, `-` and `_` requires `as` in the job, and the agent config is NOT restricted to match. — Why: I verified validateVolumeConfigName (internal/agent/volumes.go:155-165) rejects only the exact names "." and ".." and path separators, so `build.cache` is a legal volume name while `UNIFIED_VOLUME_BUILD.CACHE` is not a legal environment variable name. Restricting operator-facing names to the identifier charset would remove the asymmetry but imposes a limit nothing demands, and `as` exists precisely to decouple the handle from the name. The error already names the alias and states the permitted characters. No example or template uses such a name (grepped). — Cost if wrong: an operator with a dotted volume name forces every job using it to write one extra line.
Ruling 35: Cross-replica exclusion on Kubernetes must be atomic. "Two replicas can both pick a free volume within one pod-creation window" is a correctness hole, not a parity nicety. — Why: `exclusive` means one run at a time and unified-cd enforces it rather than trusting the access mode, precisely because RWO is node-level and two pods on one node can both mount one PVC; two concurrent Unity builds writing one Library/ is the failure the mode exists to prevent. Reading pod labels then creating a pod is a read-modify-write with no atomicity, and the implementer's own finding about agentName shows replicas sharing a config and therefore PVCs is the NORMAL case here, not an edge one. I suggested holding the PVC itself with an annotation naming the run, written under a resourceVersion CAS, with a stale holder detected by the absence of the named run's pod — no new object kind, and occupancy still derived from cluster state. What is ruled is the atomicity, not the carrier; the implementer may use a coordination.k8s.io Lease instead with its reasoning. — Cost if wrong: an extra API round trip per volume acquisition.
Ruling 36: The Kubernetes volume wait must be abandonable on drain, same as Ruling 18 required for the host agent. — Why: identical reasoning — an agent that cannot be drained cannot be rolled, and a run waiting on a busy exclusive volume would hold its slot for the holder's whole duration, tens of minutes for a Unity build. — Cost if wrong: none; this only adds a cancellation path.
Ruling 37: The artifact/cache divergence becomes its own task (new Task 10; the docs task renumbers to 11), fixed on the HOST side by resolving such a path through the mount table. This replaces Ruling 22's loud refusal. — Why: Ruling 22 made the host fail loudly to prevent silent data loss, which was right while I believed the limitation was host-only. Task 9 showed that on Kubernetes the sidecar mounts every volume so those paths genuinely work, so the same YAML now succeeds on k8s and fails on a host agent — the exact divergence this project exists to remove, with the host as the wrong side. Deliberately breaking the working k8s path for symmetry would be the wrong direction. — Cost if wrong: one more task before the branch lands; the loud refusal remains the fallback if the resolution proves unworkable.
Ruling 38: Task 9's other judgements are accepted. Not changing `imageStepEnv` was correct and MY BRIEF WAS WRONG — it seeds scope-pod creation env and scope pods mount no volume, so the variables belong on k8sBackend.VolumePaths; plan corrected. The new required `agentName` config field is accepted, because the enrolled ID `k8s:<cluster>:<ns>:<podUID>` carries colons and changes every restart, so it can neither prefix a PVC name nor survive one. `EnsurePVCs` taking a namespace is fine. Not extending PodPool.Restore is right, since occupancy is re-read from pod labels on every claim and there is nothing to adopt — but the code comment must say so. Extracting the shared `ChooseVolumes` is right, because two independent implementations of the choice would drift.
Ruling 39: The lock-to-pod window must be closed by a re-read after create, not only by a shorter timeout. — Why: nothing refreshes annoVolumeHeldAt after it is written and nothing re-checks the lock after CreatePod returns, so a create that outlives the two-minute grace lets a second replica take over and both pods mount one exclusive PVC — the exact outcome the mode exists to prevent, which RWO does not stop on one node and never stops for RWX. The reviewer grounded the reachability instead of asserting it: cmd/k8s-agent/main.go:68 builds the clientset with no QPS/Burst, so client-go's 5 QPS / burst 10 defaults apply to a single limiter shared by every pods/exec for every step, every pod List per waiting run per 5s, and every PVC call, with maxConcurrent defaulting to 100. I required three changes because they do different jobs: the post-create re-read is the correctness fix and the only one that also covers CLOCK SKEW between replicas (heldAt is written by one machine and judged by another, which no timeout addresses); the bounded create reduces how often the re-read has to save us; raising QPS/Burst attacks the root of the reachability argument. — Cost if wrong: one extra PVC read per successful create.
Ruling 40: A named agent pod template's workspace.mountPath must drive volume mounting, the step environment and the wipe, through one shared resolver. — Why: BuildPod resolves the workspace config as the agent template's overridden by the job's, but planPodVolumes was handed only the job's. With `podTemplate: {name: golang}` and an agent template setting workspace.mountPath: /src, the pod mounts the volume at /src/.cache while the step is told /workspace/.cache, and the cleanWorkspace wipe runs against an unmounted /workspace — so the one deliberate path for destroying volume data silently does nothing and the job that asked for a clean persistent workspace gets a dirty one. The /workspace fallback is pre-existing and already mis-reports UNIFIED_WORKSPACE for that template shape, which is why this is Important rather than Critical, but this change makes it load-bearing for a destructive operation. — Cost if wrong: one more shared helper.
Ruling 41: The post-create confirmation must be a CAS Update that re-stamps annoVolumeHeldAt under the resourceVersion just read, not a bare Get. — Why: `lostLock` only reads, so it never bumps the resourceVersion and cannot invalidate a rival's PENDING optimistic update. The re-reviewer gave the exact ordering: A updates (rv1); B reads rv1; B lists pods and sees none for A because A's pod is not committed yet; A's create commits; A's Get still sees itself and A execs; B's Update against rv1 still succeeds; B execs. Both pods pass their own post-create check and nothing re-checks during a run. It needs A's create-commit-to-Get to nest inside B's ListPods-to-Update, which a mutating admission webhook on pod create makes easy. This is precisely the clock-skew path Ruling 39 claimed the re-read was the only mechanism to cover — so Ruling 39 narrowed the window to one round trip rather than closing it. A CAS re-stamp costs the same number of API calls and closes the ordering in both directions. — Cost if wrong: one write where there was a read.
Ruling 42: Size the client rate limit against its real consumers AND make a timed-out create non-fatal. — Why: the comment's budget counted only the 5s occupancy Lists and omitted WaitForPodRunning, which polls Pods().Get every 500ms for the whole of each pod's start — 2 QPS per starting run, up to 200 QPS at maxConcurrent 100, four times the new sustained limit of 50. A token bucket queues without bound under over-demand, so a create POST issued during a fleet start can wait past the new 30s bound, and a timed-out create was a hard run failure rather than a retry.
