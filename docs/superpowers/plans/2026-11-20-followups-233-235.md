## Decisions (controller calls, made for the user)

- **PVC-name collision** (`<agentName>-<volume>` can be identical for agent `a-b` + volume `c` and agent `a` + volume `b-c`):
  - **User decision (2026-11-20): rename PVCs; a breaking change is acceptable.**
  - The new claim name is `<agentName>.<volume>`.
    - A PVC name is a DNS-1123 subdomain, so `.` is allowed in it.
    - Agent names and volume names are both DNS labels with no `.`, so the mapping is injective and no two pairs can collide.
    - The maximum length is 63 + 1 + 63 = 127, well under 253.
  - Old `<agentName>-<volume>` PVCs are **not** adopted, renamed or deleted automatically. The agent creates the new claim empty, and old claims are left untouched and never reclaimed.
  - Ship a migration guide, `docs/operator-manual/migrations/2026-11-20-k8s-volume-pvc-names.md`. It must cover:
    - a before→after naming table;
    - how to find the old PVCs (`kubectl get pvc -l unified-cd/volume-owner=<agentName>`);
    - a data-copy recipe (a one-off pod mounting both PVCs and running `cp -a`), for volumes whose data matters, before the first run on the new agent;
    - deleting the old PVCs afterwards.
  - Check every other place that derives a name from the claim name and keep each within its limit, for example the claim-pod label key `volume.unified-cd/<claim>`, whose name segment may be at most 63 chars. If the claim name cannot fit, switch that key to the volume name, and keep the parser in `volumes.go:97` consistent.
  - The release note marks this as breaking for Kubernetes agents.
- **Volume lock** (`volMu`):
  - Do not hold it across PVC create or annotation-sync API calls.
  - Hold it only around decisions that depend on which pods hold a volume (reclaim/delete eligibility and the delete call itself), so a pod create never waits on PVC creation.
- **Cookie names.**
  - When cookies are Secure (`!InsecureCookies`), name them `__Host-ucd_cli_login` and `__Host-ucd_cli_cb` with `Path=/` and no `Domain`. Browsers then refuse a cookie set by a sibling subdomain or over plain http.
  - With `InsecureCookies`, keep the plain names and today's narrow paths. The prefix requires Secure, and plain-http deployments are already exposed to on-path attackers.
- **Relay discovery cache.**
  - Cache the IdP discovery result used by the relay and the CLI browser-login endpoints for 10 minutes.
  - Never cache a failed discovery.
  - The web login and `verifierProvider` stay as they are.
